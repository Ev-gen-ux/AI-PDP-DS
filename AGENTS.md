# AI-PDP-DS — общий контракт

AI-коллега разрабатывает и сопровождает библиотеку дизайн-системы: компоненты, токены, иконки, графики, Figma-сопоставления и документацию. Работа заканчивается проверенным результатом с известными ограничениями. Расположение рабочей копии в worktree не меняет правила Git.

## Обязательный вход в задачу

1. Перед изменениями прочитать [tasks](docs/environment/standards/tasks.md) и [quality](docs/environment/standards/quality.md), определить scope, источники, полномочия и критерии готовности.
2. По объекту задачи открыть индекс ниже и перечисленные применимые стандарты. Для нескольких объектов объединить требования; навык добавляет процедуру и не отменяет стандарты.
3. Изучить существующий код, Spec, токены и решения перед предложением нового. Версии, API и команды проверять по исходникам, package.json и lockfile.
4. Согласованные ясные действия выполнять самостоятельно. Новые существенные решения и конфликты уточнять до зависимой реализации; фиксировать факты, предположения и решения отдельно.
5. Зафиксировать проверенные результаты и ограничения. Не объявлять неподтверждённую поставку завершённой.

## Источники и обязательные принципы

Визуальные требования существующего компонента — Figma master и принятый Component Spec. Для code-first нужен явно согласованный источник и способ приёмки. Один Spec хранит решения компонента; состояние задачи ссылается на него. Конфликт источников не разрешается угадыванием.

Исходники токенов и генератор обеспечивают воспроизводимую тему; производные файлы не редактируются вручную. В компонентах только семантические токены, строгие типы, согласованный API и существующий Icon-слой. Стилизация — styled-components; новые библиотеки/источники токенов не вводятся попутно. Экраны — типизированные React-компоненты, без JSON-композиции.

Фактическая реализация, поддержанные версии и доступные инструменты проверяются отдельно от проекта будущих возможностей. Наличие схемы, текста навыка или read-only роли не является техническим ограничением инструмента. Разрешения задаёт клиент/sandbox.

## Полномочия и поставка

Работать в отдельной ветке; main не изменять напрямую. Изменения через review/PR, версии по [releases](docs/environment/standards/releases.md). Не обходить защиту, проверки или TypeScript. Не менять глобальные настройки агентов, GitHub Secrets и защиту ветки без явного поручения.

Публикация, платная генерация и запись во внешние библиотеки требуют соответствующих полномочий; наличие roadmap/workflow их не предоставляет. Аудит не разрешает скрытую реализацию. Секреты не включаются в Git и публичные материалы.

Общий контракт и стандарты изменяются как отдельная порученная работа среды. Инструкции пользователя и уже предоставленные полномочия учитываются до запроса повторных подтверждений.

## Состояние и навигация

[Onboarding](docs/environment/onboarding.md) описывает запуск и адаптеры. [Подготовка](docs/environment-preparation.md) хранит рабочую базу и возврат; [roadmap](ENVIRONMENT_ROADMAP.md) — будущие направления. Согласованная архитектура общего ядра и подсред принята в решении 001.

Первая проверяемая платформа — текущая React web-библиотека; Android/iOS идут отдельным этапом после приёмки веб-среды. Для длительных задач доступен [CLI состояния](docs/environment/workflows/task-state.md): безопасный init, resume/check и обновления с контролем ревизии. [Карта навыков P0.5](docs/environment/skills.md) направляет к каноническим SKILL.md и рабочим директивам. Их наличие не доказывает обнаружение клиентом; клиентские hooks и испытания совместимости выполняются отдельно.

[Диагностика среды](docs/environment/workflows/environment-checks.md): env:check проверяет структуру, env:route выдаёт декларативный маршрут; PASS не означает приёмку результата или проверенное поведение клиента.

Архив docs/environment/references и исторические исследования — справка, не второй активный контракт. Не загружать старые инструкции как нормативные. До завершения миграции каждый перенесённый источник отслеживается в карте и реестре переноса.
