# Брифование задачи

## Назначение и запуск

Применять после [intake](intake.md) для новой задачи или существенных новых вводных. Ведущий сам проводит интервью и составляет бриф; готовая форма не заменяет выяснение задачи. Глубина зависит от ближайшего результата.

## Входы

Поручение и принятые решения, STATE, материалы выбранной системы, действующий Spec, исходники/Figma по необходимости. Для новой системы использовать [системный бриф](../templates/specifications.md#system-brief), для остальных задач — [форму брифа](../templates/specifications.md#brief).

## Условия начала

Известны действие, объект и выбранная система; для новой системы сначала создан её Discovery-контейнер по [созданию](system.md). Не начинать повторное интервью, пока не прочитаны уже имеющиеся ответы и источники.

## Этапы

1. Извлечь известное: подтвердившие источники, предположения, неизвестное и противоречия. Проверить, что пользователь просит сейчас: исследование, обсуждение, реализацию или продолжение.
2. При минимальных вводных задать небольшой раунд вопросов на ширину задачи с понятными вариантами. Уточнять только то, что влияет на результат; технические решения, которые ведущий может обоснованно предложить, не перекладывать на владельца.
3. Разобрать ответы: что стало понятно, какой существенный пробел остался, какие ответы конфликтуют. Следующий раунд посвятить этим пробелам без фиксированного числа повторений. Если ответ «не знаю», предложить варианты или исследование и сохранить неизвестное открытым.
4. Консолидировать brief.md внутри задачи. Отделить подтверждённое от предположений и открытых вопросов; включить scope, источники, ограничения, критерии и следующий шаг. Показать краткую сводку понимания, учесть поправки. Не требовать нового подтверждения уже принятого ответа.
5. Проверить достаточность по маршруту:

| Маршрут                    | Что должно быть известно до зависимой реализации                                                                                                                                                                                    |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Новая система              | Назначение/потребители, источник и версия фундамента, поставка storybook/figma/both, темы, ограничения и критерии. Технический шаблон разворачивается после достаточного согласованного брифа по [project-setup](project-setup.md). |
| Новый/изменённый компонент | Назначение, поведение/API, композиция, варианты/состояния, токены, доступность, источники и критерии. Единственный [Spec](../templates/specifications.md#component-spec) согласовывается до реализации.                             |
| Ремонт                     | Симптом, воспроизведение, ожидаемое принятое поведение, границы и способ проверки. Полный новый системный бриф не требуется.                                                                                                        |
| Примитивы/типографика      | Точные ключи/значения и происхождение, сохраняемые defaults, связанные последствия, шрифтовые ресурсы и поставка по [примитивам](primitive-values.md).                                                                              |
| Аудит/исследование         | Объект, вопрос, критерии, источники и границы; поручение на анализ не превращается в поручение исправить.                                                                                                                           |

6. Убрать BRIEF:DRAFT после заполнения. Для Spec убрать SPEC:DRAFT и записать реальное согласование текущего хеша через approve-spec. Выполнить refresh после изменения входов и перейти ready → implementation только при выполнении [условий STATE](task-state.md).

## Решения владельца

Существенные продуктовые/API/визуальные решения и новый план примитивов предъявлять владельцу до зависимой работы. Предположение и отсутствие ответа не считаются решением. Повторное разрешение на уже согласованный технический шаг не требуется.

## Результат

Достаточный бриф задачи; принятые решения и конкретные открытые вопросы в STATE. Компонентные матрицы находятся в единственном Spec, без копирования в отдельные анкеты/таблицы. Новый журнал «раундов брифа» не создаётся по умолчанию.

## Проверка

Проверить, что нет блокирующего неизвестного для ближайшего шага, критерии наблюдаемы и следующий шаг определён. Матрица полей сама по себе не доказывает понимание задачи. Refresh не делает старые проверки актуальными и не согласовывает Spec.

## Продолжение и возврат

Замечание уточняет затронутый блок существующего брифа. Существенная смена цели возвращает задачу в discovery; независимая согласованная часть может продолжаться. Далее выполнять предметную директиву выбранного маршрута; отдельный state.json не создавать.
