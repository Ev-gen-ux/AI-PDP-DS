# Проверка и передача результата

## Назначение и запуск

Использовать перед review и передачей результата любой предметной процедуры. Выполнение проверки, фактическая поставка и приёмка владельца — отдельные события.

## Входы

Актуальные критерии brief/Spec, diff, STATE, артефакты и [качество](../docs/standards/quality.md). Для кодовой и Figma-поставки использовать их собственные проверки.

## Условия начала

Известен предъявляемый результат и выбранные методы по его влиянию. Не приписывать результат чужому fingerprint или старому источнику.

## Этапы

1. Выполнить проверки по фактическому diff и критериям. Для кода — [code-delivery](code-delivery.md), для Figma — [figma-delivery](figma-delivery.md), для both — также [паритет](figma-parity.md). Для read-only анализа достаточно проверки отчёта/источников; ненужную реализацию не запускать.
2. Сохранить методы, версии/даты, результат, evidence и ограничения внутри задачи. Разделять automated/manual и pass/fail/not-run/not-applicable. Для not-applicable нужна причина; пропущенное не становится PASS.
3. Выполнить resume/check [журнала](task-state.md). Изменившиеся входы требуют разбора diff и новых затронутых проверок; refresh не переисполняет evidence. Обновить Verification единственного Spec при компонентной работе.
4. Получить нужный ограниченный review по [координации](coordination.md). Отличать фактический отдельный review от самопроверки. Исправить обоснованные находки и повторить затронутые проверки.
5. Передать конкретный результат: что изменилось и почему, где находится, как проверено и какие существенные ограничения остались. Отметить раздельную готовность кода/Figma и фактическую публикацию.
6. Перейти в review. Accepted записать только по реальной приёмке текущего результата владельцем. Одноразовые данные очищать по уже согласованному порядку после проверенного завершения работы, сохраняя предметную историю проекта; очистка не назначает приёмку.

## Решения владельца

Приёмка конкретного результата и существенные исключения привязаны к текущим входам. Разрешение следующего этапа/публикации не выводить автоматически из технического PASS.

## Результат

Предъявленный проверяемый результат, актуальный STATE и evidence. Невыполненное/недоступное явно видно; статус review означает готовность к рассмотрению.

## Проверка

Сопоставить каждый заявленный результат с реальным методом/evidence. Сборка, реальное поведение, визуальный паритет, ручная a11y и публикация не подменяют друг друга. Исключение содержит criterion, owner note и fingerprint.

## Продолжение и возврат

Замечание возвращает задачу в implementation либо к затронутому брифу/Spec; изменения делают старые проверки неактуальными. Новые задачи и внешние действия начинаются только в порученном scope.
