# Компонент: создание, доработка, ремонт

## Назначение и запуск

Использовать после [intake](intake.md) для одного компонента. Выбрать создание/изменение контракта либо ремонт принятого поведения и порученную поставку.

## Входы

Бриф и STATE, принятый Spec, публичные props/exports, стили, токены, stories и Figma/source по выбранной поставке. Прочитать [компоненты](../docs/standards/components.md), [доступность](../docs/standards/accessibility.md), [токены](../docs/standards/tokens.md) и [качество](../docs/standards/quality.md).

## Условия начала

Выбраны проект и задача. Прочитать актуальные источники и проверить возможность расширить существующий компонент. Недостающие вводные получить через [брифование](briefing.md). Противоречие master и принятого Spec разрешается до зависимой правки.

## Этапы

1. Для create/refine заполнить один [Spec](../templates/component-spec.md) в component-specs/<id>/spec.md: назначение, API, варианты, Numeric Map, State Token Matrix, Hard Constraints, композиция, поведение/a11y и Verification. Не изобретать числа по соседу.
2. Предъявить существенный контракт владельцу и записать approve-spec текущего содержимого после реального согласования. До реализации в коде или Figma контракт должен быть принят. Новая ось/значение props сначала попадает в Spec.
3. Для repair воспроизвести симптом и установить ожидаемое поведение по принятому контракту. Отделить причину от гипотезы; выполнить достаточную локальную правку, сохраняя остальной API. Для старого компонента без Spec зафиксировать краткий контракт источников и границы ремонта, без выдуманного полного дизайна.
4. Собрать согласованную композицию. Label и Inline Message использовать как существующие компоненты/instances с их собственными props/семантикой. Родитель владеет токенами своего тела; вложенные компоненты не разворачивать ради перекраски.
5. Выполнить нужную [кодовую](code-delivery.md) и/или [Figma-поставку](figma-delivery.md). Матрицы соразмерны компоненту: не придумывать hover/loading у неинтерактивного элемента.
6. Для both проверить [паритет](figma-parity.md), обновить Verification единого Spec и [передать](verify-deliver.md) результат.

## Решения владельца

Новый или изменённый компонентный контракт принимается до зависимой реализации. Если ремонт меняет контракт, перейти к refine и согласовать затронутое решение. Ремонт в принятых границах не требует полного нового интервью.

## Результат

Один актуальный Spec, согласованная реализация в выбранных носителях, соответствующие exports/stories или Figma-ссылки и доказательства проверок в задаче. Следующая самостоятельная задача компонента получает tasks/<task-id>, сохраняя общий Spec.

## Проверка

Проверка ремонта воспроизводит исходный симптом и подтверждает исправленное поведение. Для визуальной правки проверить реальные состояния/темы/размеры; jsdom и Storybook build не доказывают геометрию. Выполнить применимые требования Spec и выбранной поставки.

## Продолжение и возврат

Замечание возвращает текущую задачу в implementation; существенное изменение цели/контракта — к брифу/Spec. Повторять затронутые проверки, сохраняя незатронутые решения. Не создавать второй Spec или заново весь компонент.
