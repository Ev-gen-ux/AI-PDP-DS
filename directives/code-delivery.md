# Кодовая поставка

## Назначение и запуск

Использовать из системной, компонентной или токенной процедуры для storybook/both. Подготовить работающую библиотеку и её Storybook по согласованному объёму. Для figma-only эта ветка не требуется.

## Входы

STATE и бриф задачи, принятый Component Spec при компонентной работе, текущие исходники, токены, package/lock, configs, scripts и профиль проверок выбранной системы. Применять [компоненты](../docs/standards/components.md), [доступность](../docs/standards/accessibility.md), [токены](../docs/standards/tokens.md) и [качество](../docs/standards/quality.md).

## Условия начала

Выбран проект и согласован результат; технический фундамент существует по [развёртыванию](project-setup.md). Новый/изменённый контракт компонента принят до реализации. Для ремонта достаточно принятого поведения и воспроизведения. Проверить реально доступные команды по package.json.

## Этапы

1. По фактическому diff выбрать проверки: локальный ремонт, компонентное изменение либо полный выпуск/передача. Подготовка отдельного компонента не запускает полный релиз автоматически.
2. Реализовать согласованную часть через публичные props/exports и существующую композицию. Label/Inline Message сохраняют собственную семантику; значения тела берутся из его токенов. Технические детали компонента задаёт [компонентная процедура](component.md).
3. После изменения токенов запустить генератор проекта и проверить его diff. Подключить выбранные шрифтовые ресурсы по [примитивам](primitive-values.md), проверить загрузку и метрики; generated CSS/TS вручную не подменять.
4. Обновить stories и пользовательские примеры по существующему формату. Показать затронутые варианты, состояния, темы, адаптивность и реальные взаимодействия. Неприменимые состояния не выдумывать.
5. Выполнить нужные typecheck, тесты, lint, сборку и Storybook по профилю проекта. Проверить затронутые визуальные состояния в реальном рендере; автоматическая сборка геометрию не подтверждает.
6. При выпуске/самостоятельной передаче проверить содержимое пакета, публичные exports/types, CSS/fonts и документацию подключения. Подготовить [экспорт](project-export.md) в новую папку, установить зависимости по собственному lock и выполнить необходимые build/Storybook/проверки и подключение в изолированном consumer без родителя. Пробные зависимости и outputs не добавлять в исходники передаваемого проекта.

## Решения владельца

Изменение API/визуального контракта, состава поставки, совместимости и существенные исключения проверок. Git/npm/Chromatic и другие публикации требуют соответствующего явного поручения; подготовка кода его не заменяет.

## Результат

Рабочий код и Storybook в выбранном объёме, актуальные примеры и методы/результаты проверок в задаче. Для порученной передачи — конкретный пакет/папка и инструкция подключения с фактическими ограничениями.

## Проверка

Сопоставить результат с API, состояниями и критериями Spec/брифа. Разделить функциональную, визуальную и ручную a11y-проверку. Для both дополнительно пройти [паритет](figma-parity.md); работоспособность Storybook не подтверждает Figma-поставку. Пропущенные проверки остаются not-run.

## Продолжение и возврат

После замечания повторить затронутые действия и проверки. Изменение контракта возвращает к Spec, данных примитивов — к их плану, технического фундамента — к project-setup. Не пересоздавать библиотеку и не переиспользовать устаревший evidence. Завершить по [передаче](verify-deliver.md).
