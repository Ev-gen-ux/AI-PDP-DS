# Развёртывание технического проекта

## Назначение и запуск

Выполнять из [создания системы](system.md) после достаточного брифа. Подготовить выбранный технический фундамент внутри projects/<id>. Эта процедура направляет действия ведущего; create и install-tooling не являются генераторами React-библиотеки.

## Входы

Заполненный [системный бриф](../templates/system-brief.md), STATE задачи, источник и версия технического шаблона/фундамента, состав поставки storybook/figma/both, темы, ограничения и критерии запуска. Требования результата — [архитектура](../ARCHITECTURE.md), [токены](../docs/standards/tokens.md) и [качество](../docs/standards/quality.md).

## Условия начала

Имя/ID и папка проекта определены; существенные решения по поставке и фундаменту приняты. Проверить наличие, состав и возможность использования выбранного шаблона. Если готового шаблона нет, явно предложить источник или подготовку каркаса в scope задачи; не объявлять несуществующий starter доступным. Не использовать неприкреплённый latest вместо выбранной версии.

## Этапы

1. Прочитать существующие файлы и определить новый запуск или доработку. Составить список создаваемого и изменяемого; сохранять Discovery, Spec, ручные правки и историю проекта.
2. Зафиксировать в брифе источник/версию шаблона, токенов, режимов и выбранный стек. Согласовать различия кода и Figma по логическим ключам. Эталонную библиотеку заказчику не перекрашивать.
3. Для storybook/both развернуть React/TypeScript-каркас с собственными package/lock, зависимостями, configs, src, tokens, генератором, Storybook и необходимыми scripts. Взять версии из согласованного шаблона/профиля; не менять стек существующего проекта попутно. Числовые значения и шрифт не назначать по примеру.
4. Для figma подготовить собственную целевую библиотеку и необходимые проектные источники/документы; не устанавливать React/Storybook без потребности. Запись в файл проходит [Figma-поставку](figma-delivery.md). При необходимости локальной матрицы нормализовать согласованный снимок в поддерживаемый JSON без изменения семантики.
5. При необходимости установить независимые инструменты процесса: `npm run env:project -- install-tooling <id>`. Конфликты управляемых файлов разобрать до обновления; эта команда не копирует исходники системы, клиентский бренд или историю AI-PDP-DS.
6. Настроить собственные пользовательские docs и команды запуска. Пройти [примитивы](primitive-values.md), затем выбранную [кодовую](code-delivery.md) и/или [Figma-поставку](figma-delivery.md) по текущему объёму.

## Решения владельца

Источник и версия фундамента, поставка, существенный выбор стека и изменение принятой архитектуры. Рутинные действия выбранного развёртывания выполнять в уже данных полномочиях. Новые компонентные контракты согласовываются отдельно до реализации.

## Результат

Внутри проекта находится согласованный фундамент и техническая среда выбранной поставки, её версии, команды и документация. Нет импортов/extends из разработчика, общего npm workspace или зависимости от родительского node_modules. Все продуктовые материалы остаются в проекте.

## Проверка

Проверить фактический запуск и генерацию; для кода — сборку и Storybook, для Figma — реальный состав и привязки целевой библиотеки. Самостоятельную передачу подтвердить в отдельной копии по [поставке](code-delivery.md), когда она входит в задачу. Наличие папок и успешный install-tooling не подтверждают работающий продукт.

## Продолжение и возврат

Повторный запуск сравнивает текущий проект с выбранной версией и вносит нужный diff; папка не пересоздаётся. Конфликт исходников возвращает к решению по фундаменту, недостающие требования — к [брифу](briefing.md). Недоступную поверхность отметить not-run и продолжать независимую разрешённую часть. Завершить по [передаче](verify-deliver.md).
