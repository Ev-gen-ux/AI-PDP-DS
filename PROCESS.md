# Процесс design-system-developer

Вход — [AGENTS](AGENTS.md).

Действующая согласованная модель: каждая дизайн-система — самостоятельная папка. Общие инструменты находятся в разработчике; все материалы конкретной системы находятся внутри неё. product-discovery, component-specs и src — соседние папки. Новые задачи используют STATE в Markdown-журнале, без отдельного state.json.

## 1. Вход и ответственность

Профиль основного ведущего инженера и архитектора канонически задан в [AGENTS](AGENTS.md). Он ведёт брифование, исследует источники и выполняет согласованные технические действия. Владелец принимает существенные продуктовые/API/визуальные решения и результаты.

**Запрос → выбор системы и директивы → достаточный бриф → исследование по необходимости → согласование контракта → выполнение → проверка → review → приёмка.**

Общий вход — [intake](directives/intake.md), интервью — [briefing](directives/briefing.md). Пользователь не обязан знать имена скиллов или команды. env:route --request предлагает маршрут по ключевым словам; агент проверяет смысл и контекст, а не объявляет подсказку полноценным семантическим оркестратором.

До начала работы определить систему, действие, объект, платформу, поставку, границы и критерии готовности. При неоднозначной системе уточнить выбор до записи. Продолжение/замечание относится к текущей задаче; самостоятельный новый результат получает отдельную задачу.

## 2. Создание проекта дизайн-системы

Папка системы создаётся сразу после определения имени/ID, до её Discovery. [Директива создания](directives/system.md) использует env:project create: команда создаёт system.json и product-discovery с брифом/журналом. Это рабочий контейнер, не готовая библиотека.

В этой папке выполняются брифование, исследование, выбор решений и развитие системы. Внешние workspace/environment/intakes для продуктовых задач не создаются.

После достаточного согласованного брифа ведущий проходит [развёртывание проекта](directives/project-setup.md) и подготавливает выбранный версионированный технический шаблон в этой папке. Для storybook/both нужен самостоятельный кодовый проект; figma-поставка не требует установки React/Storybook. Create и install-tooling сами техническую библиотеку не генерируют.

Бриф определяет назначение, аудиторию/продукты, платформу, источники, ограничения, темы и Figma/code-поставку. Исследование существующих решений сохраняется в product-discovery/research с вопросом, методом, первичными источниками/датами, сравнением, выводом и ограничениями. Принятые решения — рядом в decisions. Кабинетный анализ не выдаётся за проведённые пользовательские тесты.

Затем пройти [настройку примитивов](directives/primitive-values.md): данные текстом/файлом → матрица → согласованный план → значения → генерация и выбранная поставка. Семантика, типы, режимы и aliases сохраняются. Типографика произвольная, включая ресурсы заказчика и Google Fonts по его указанию. Матрица — представление, tokens/primitives — канонические значения проекта.

Сначала использовать известное из запроса, кода, Spec и решений, затем задавать только существенные вопросы небольшими раундами. Для ясного ремонта достаточно краткой постановки с воспроизведением; повторное полное интервью не требуется. Факты, предположения и блокирующие вопросы разделяются.

Скилл и отдельный агент выбираются по [координации](directives/coordination.md): первый задаёт процедуру, второй выполняет фокусную подзадачу. Перед запуском ведущий читает роль из agents/ и передаёт её инструкции через доступный инструмент делегирования. Регистрация ролей через .codex не используется. Без такого инструмента ведущий выполняет работу сам, без заявления об отдельном исполнителе. Простой ясный результат не требует отдельного агента.

Предметная процедура определяет контракт и изменение. Для storybook выбирается [кодовая поставка](directives/code-delivery.md), для figma — [Figma-поставка](directives/figma-delivery.md), для both — обе с [паритетом](directives/figma-parity.md). При анализе/аудите эти ветки не означают автоматическую реализацию.

Директивы используют [общий формат](templates/project-instructions.md#directive): назначение/запуск, входы, условия начала, этапы, решения владельца, результат, проверка, продолжение/возврат. PROCESS задаёт общий маршрут, directives — действия, docs/standards — требования, templates — формы. Скиллы выбирают нужные процедуры по config/routes.json; второй workflow рядом с PROCESS не создаётся.

## 3. Компоненты

Для каждого компонента одна папка component-specs/<component-id>. В ней spec.md — единственный контракт: поведение/API, варианты, состояния, матрицы токенов, числовые значения, композиция, доступность, ограничения и критерии готовности. Не создавать дублирующие Props/State Matrix документы.

Бриф и журнал первоначальной работы находятся рядом. Если появляется отдельная следующая задача того же компонента, её brief/журнал находятся внутри tasks/<task-id> этой папки, а Spec остаётся общим. Этот вложенный каталог создаётся только при необходимости.

Сначала подготовить и предъявить спецификацию одного компонента. После реального согласования записать approve-spec с примечанием владельца и хешем текущего Spec; только затем переходить к реализации в src/components/<component-id>. Не требуется заранее описывать всю библиотеку. Для локального ремонта принятого контракта новое полное согласование не требуется; изменение контракта относится к refine и требует приёмки изменённой спецификации.

Figma master/принятый Spec определяют визуальный контракт; конфликт не разрешается угадыванием. Компонент владеет токенами своего тела. Label, Inline Message и другие вложенные компоненты сохраняют собственные свойства и семантику.

## 4. Источники истины

| Место                               | Назначение                                                                             |
| ----------------------------------- | -------------------------------------------------------------------------------------- |
| product-discovery                   | Бриф, исследования и решения по системе в целом                                        |
| component-specs/<component>/spec.md | Живой технический контракт одного компонента                                           |
| brief.md задачи                     | Поручение, scope, источники, критерии и вопросы; ссылка на Spec без копирования матриц |
| \_process_log.md задачи             | STATE и существенные вехи этой работы                                                  |
| src                                 | Реализация; код создаётся здесь во время разработки                                    |
| docs                                | Подключение, применение, темы и сопровождение библиотеки                               |
| Evidence внутри задачи              | Необходимые доказательства конкретных проверок                                         |
| Инструкции разработчика             | Общая методика и инструменты; продукт не импортирует их для сборки                     |

STATE — единственное актуальное состояние задачи. Он расположен между STATE:START/STATE:END в самом Markdown. Поля сериализуются в Markdown-список с JSON-значениями; отдельного файла состояния нет. Человеческий текст вне блока сохраняется при обновлении. История содержит необходимые прежние Markdown-ревизии.

В STATE хранятся ID/система, действие/объект, статус/ревизия, scope, ссылки и хеши brief/spec/inputs, вопросы, решения, evidence, исключения и следующий шаг. Наличие валидного блока не удостоверяет личность автора решения или полноту требований.

## 5. Состояния

| Состояние      | Условие                                                                                                                          |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| discovery      | Уточнение постановки; неизвестные остаются открытыми                                                                             |
| ready          | Заполненный бриф, известные title/scope/nextStep, нет блокирующих вопросов; для create/refine компонента согласован текущий Spec |
| implementation | Выполнение согласованного scope и проверки                                                                                       |
| review         | Результат предъявлен, проверки и ограничения видимы                                                                              |
| accepted       | Реальная приёмка владельцем конкретного fingerprint и соответствующие evidence                                                   |
| blocked        | Явная причина зависимости; независимая разрешённая часть может продолжаться                                                      |
| paused         | Пауза по указанию владельца; сохраняется прежний рабочий этап                                                                    |
| cancelled      | Задача отменена; это не успешная реализация                                                                                      |

Основной переход: discovery → ready → implementation → review → accepted. Замечание возвращает review в implementation; изменение цели — в discovery. Переходы проверяет CLI. Отмена/пауза исполняются по запросу владельца, без самостоятельного назначения приёмки.

Новые важные решения уточняются до зависимой реализации. Уже предоставленные полномочия сохраняются; рутинные шаги не требуют повторного формального approval. Отсутствие ответа не является согласием.

## 6. Проверка и приёмка

Методы выбираются по влиянию: локальная правка, компонент либо выпуск. Использовать существующие scripts/tests; новый тест нужен для поведения/регрессии, а не количества. Сборка не доказывает взаимодействие, визуальный паритет, доступность, опубликованную связь Figma или приёмку.

Evidence сохраняет criterion, kind, method, result, fingerprint и artifacts с хешами. Результаты: pass/fail/not-run/not-applicable. Исключение содержит criterion, owner note и fingerprint. Не выполненная проверка остаётся not-run. Приёмка допускает конкретное согласованное исключение, не превращая его в PASS.

Изменение входов делает старые проверки устаревшими. Refresh обновляет снимок входов, но не переатрибутирует evidence/исключения и не согласовывает новый Spec. Старая приёмка сохраняется в истории; текущий accepted при изменениях возвращается в review.

Принятое «дальше» учитывается по контексту. Разрешение продолжать не означает прохождение невыполненных проверок. Commit/push/PR/publish и внешние записи выполняются только по соответствующему явному поручению. Иконки/графики исключены до нового явного поручения.

## 7. Восстановление

В новом чате прочитать AGENTS, выбранную систему, её журнал/brief/Spec и актуальное поручение. Выполнить resume/check; проверить scope, входы, evidence и следующий шаг. Не брать произвольную задачу по mtime и не повторять закрытый бриф.

Запись требует актуального token, использует lock, проверяет файл перед атомарной заменой и сохраняет прежнюю Markdown-ревизию. Конфликт требует перечитать состояние; чужой lock не удаляется автоматически. Пути не выходят из проекта через .. или symlink. Секреты не становятся evidence.

Нужные исторические JSON v1 сохранены внутри history системы как неизменённые свидетельства своей версии. Их исполняемый runtime удалён; новые задачи используют только STATE журнала. Старый receipt не перепривязывается к новым входам.

## 8. Передача и границы реализации

Система содержит собственные package/lock, configs, scripts, Storybook, спецификации, Discovery и историю. Передача проверяет копию одной папки вне разработчика: установка, сборка, нужные tests/quality, Storybook и локальные ссылки. Родительские scripts/config/node_modules и .git не являются обязательными зависимостями.

Реализованы Markdown-журнал, переходы/согласование Spec, поиск проекта, контейнер новой системы, подсказка маршрута, канонические директивы/стандарты и переносимый набор инструментов. Его установка через env:project install-tooling копирует версию внутрь системы, проверяет конфликты и не меняет её автоматически при обновлении разработчика.

AI-PDP-DS перенесена в projects/ai-pdp-ds; её независимость проверяется отдельным install/build/Storybook по журналу Discovery. Полный генератор нового React-проекта не реализован. Текущее размещение описано в ARCHITECTURE. Тест копирования инструментов не выдаётся за проверку передачи всей библиотеки. Декларации скиллов/ролей проверяются отдельно от фактического запуска исполнителя.

Один проект из projects/<id> передаётся самостоятельно по [экспорту](directives/project-export.md). Локальная подготовка папки не означает поручение commit/push или создания remote-репозитория.

## Обслуживание разработчика

Будущие улучшения самой среды находятся в [BACKLOG](BACKLOG.md). Для выполняемой работы используется временная задача .local/tasks/<id>, создаваемая через env:task init <id> --object environment. Её журнал и доказательства нужны во время выполнения и проверки; после проверенного завершения в согласованной очистке удаляются. Постоянный корневой журнал и история перестройки не ведутся. Это не меняет статусы и историю продуктовых задач внутри projects/<id>.
