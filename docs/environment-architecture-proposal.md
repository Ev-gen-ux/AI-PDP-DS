# Проект архитектуры среды AI-PDP-DS

Статус: проект P0.2 для рассмотрения владельцем. Активным контрактом остаётся `CLAUDE.md`. Создание этого документа не подключает новые инструкции.

Основания: [roadmap](../ENVIRONMENT_ROADMAP.md), [план](environment-rebuild-plan.md), [исследование](environment-research-2026-11-20.md), [deep research](environment-deep-research-2026-11-20.md), [подготовка и возврат](environment-preparation.md). Исходная ревизия этапа: `65e5a94e50880296579d61a5dc11c95db1f35b1e`.

## 1. Общее ядро и подсреды

Вся архитектура Work Environment служит референсом: корневой контракт выбирает предметную подсреду, та выбирает рабочую процедуру и инструменты. Для AI-PDP-DS общее ядро отвечает за источники истины, полномочия, маршрутизацию, состояние задач и единый формат доказательств. Предметные подсреды специализируют выполнение.

| Подсреда          | Собственная ответственность                                  | Передача другим подсредам                                    |
| ----------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| Компоненты        | API, варианты, анатомия, поведение, React-реализация         | Заявка на токен/иконку; Spec и stories для проверки          |
| Токены и темы     | Исходные JSON, имена, режимы, генерация и diff               | Изменённые значения и затронутые потребители                 |
| Иконография       | Паспорт стиля, исходный SVG, доработка и экспорт             | Принятый ассет через существующий Icon-слой                  |
| Графики           | Данные, опции, lifecycle, framework wrapper                  | Компонентный контракт и доказательства данных/взаимодействий |
| Figma             | Чтение источника, сопоставления, parity и разрешённые записи | Версия источника, различия и статус mapping/публикации       |
| Документация      | Спецификации, Storybook, Foundations, миграции               | Актуальные примеры и генерируемые сведения                   |
| Качество и выпуск | Проверки, review, совместимость, отчётность, release         | Результаты с ревизией, ограничения и условия выпуска         |

Подсреда — граница ответственности. Отдельный агент, npm-пакет или MCP-сервер для каждой области не требуется. Запрос «исправь компонент» может пройти через несколько подсред в рамках одной задачи и уже предоставленных полномочий.

## 2. Источники истины

- Визуальные требования и числовые значения существующего компонента — действующий Figma master и согласованная спецификация по текущему контракту.
- Принятые решения по компоненту — один существующий Component Spec. Состояние задачи ссылается на него и не копирует матрицы.
- Токены — версионируемые исходники и согласованный процесс синхронизации с Figma; производные CSS/TS не редактируются вручную.
- Фактический API, экспорты, версии и доступные команды извлекаются из кода и конфигураций. Предлагаемый машинный индекс генерируется из этих источников.
- Доказательство проверки содержит ревизию/хеш входа, команду или способ ручного review, результат, время и ограничения. Изменение входа делает зависимое доказательство устаревшим.
- Исторический roadmap и архив не становятся вторым активным стандартом. Противоречие источников оформляется как решение с указанием владельца и влияния.

## 3. Предлагаемые файлы и подключение

Все пути ниже будущие, кроме уже существующих файлов библиотеки и спецификаций.

```text
AGENTS.md                         общий контракт и обязательная маршрутизация
CLAUDE.md                         вход Claude, направляющий к общему контракту
cursor_instruction.md             онбординг и адаптер Cursor
.agents/skills/ds-*/SKILL.md       канонические роли и выбор процедуры
docs/environment/
  standards/                      tasks, components, tokens, icons, accessibility,
                                  figma, documentation, quality, releases, governance
  domains/                        индексы подсред: стандарты, workflows, tools, выходы
  workflows/                      законченные процедуры выполнения
  references/                     примеры, нюансы, исторические инциденты
  decisions/                      принятые изменения правил и архитектуры
  onboarding.md                   настройка проекта и версий
scripts/environment/              диагностика, индекс, проверка схем и ссылок
.local/tasks/<task-id>/            локальное состояние и журналы задачи
docs/*-component-spec.md           существующие канонические спецификации
src/, tokens/, .storybook/         существующая библиотека
```

Общий контракт прямо требует читать применимые стандарты по объекту и действию задачи. Навык добавляет процедуру; отсутствие активированного навыка не отменяет стандарт. Индекс подсреды перечисляет ссылки на общие требования и свои инструменты, не переписывая нормативный текст.

У каждого навыка один канонический экземпляр в `.agents/skills`. Регистрация в Claude/Cursor проверяется адаптером: поддержанная ссылка или материализованный экспорт с контролем совпадения. Подключение проверяется из корня и подпапки; одинаковые тексты в нескольких обнаруживаемых каталогах не создаются автоматически. Проектирование не предполагает, что поле frontmatter технически ограничивает права.

У явно запускаемой директивы миграции/публикации есть границы, результат, проверки и откат. Внутренние рабочие директивы хранятся как workflows: навык читает их при выполнении порученной задачи. Такое именование сохраняет два уровня исходной среды и исключает конфликт «архивировать все директивы».

## 4. Маршрутизация задач

Общие признаки: действие, объект, платформа, поставка, разрешённые изменения, источник и ревизия. Основной профиль первой версии — web/React и Codex. Другие агентские клиенты проходят отдельную проверку; другие UI-фреймворки и native не объявляются поддержанными по одному наличию токенов.

| Запрос                   | Обязательное чтение                                                               | Процедура и результат                                                                             |
| ------------------------ | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Создать компонент        | tasks, components, tokens, accessibility, documentation, figma, quality, releases | Intake → существующие решения → Spec → существенные решения → реализация → проверки → docs/review |
| Исправить/доработать     | Те же стандарты по затронутым аспектам, существующий Spec                         | Причина → минимальный diff → регрессионная проверка → обновление Spec/evidence                    |
| Изменить токен/тему      | tasks, tokens, quality, releases                                                  | Источник → согласование изменения → generation diff → затронутые компоненты/Foundations           |
| Создать/исправить иконку | tasks, icons, tokens, figma при поставке, quality                                 | Паспорт/эталоны → выбранные SVG → техническая и визуальная проверка → Icon-интеграция             |
| Разработать график       | tasks, components, tokens, accessibility, quality, документация                   | Контракт данных → независимое ядро → React wrapper → состояния/lifecycle → review                 |
| Аудит                    | tasks, quality и предметные стандарты                                             | Findings с evidence; изменения только в отдельно порученной работе                                |
| Документация             | tasks, documentation, quality                                                     | Проверка фактов по реализации → правка описания → ссылки/сборка при необходимости                 |
| Выпуск                   | tasks, releases, governance, quality                                              | Совместимость/changeset → review → разрешённая публикация → проверка фактического результата      |
| Изменить среду           | tasks, governance, quality; roadmap и проект миграции                             | Карта правил → рассмотрение изменений политики → последовательные коммиты → испытания → откат     |

Матрица определяет применимость, а не требует полный опрос для каждого изменения. Сокращение существующих компонентных gates — отдельное предложение D1 ниже, до принятия действует текущий контракт.

## 5. Карта переноса без потери текста

[Машиночитаемая карта](environment-rule-map.json) сохраняет исходный текст, файл, строки, раздел, предлагаемый единственный будущий источник, применимость, способ подключения и проверки. Зафиксированы SHA-256 шести источников: CLAUDE, Cursor onboarding, шаблон Component Spec, шаблон PR, CODEOWNERS и roadmap владельца. Каждая содержательная строка, включая примеры, имеет запись назначения.

Текстовое покрытие не доказывает смысловую эквивалентность. Запись может включать контекст, условие или часть многострочного требования; объединение дублей и разбиение составных правил выполняются при переносе с обратными ссылками на все исходные записи. `approved: false` означает проект назначения, а не разрешение отменить требование. Предложенные проверки не объявлены уже реализованными.

| Семейство                                   | Источники                                            | Предлагаемый основной источник                                        |
| ------------------------------------------- | ---------------------------------------------------- | --------------------------------------------------------------------- |
| Полномочия/источники/запреты                | CLAUDE введение, §1, §12; Cursor §4                  | AGENTS + ссылки на предметные стандарты                               |
| Kickoff, stop/clarification, Spec и матрицы | CLAUDE §0, §14; Spec template                        | standards/tasks + существующий Spec template                          |
| Типизация, файлы, стили, API                | CLAUDE §0.5, §3, §6–7                                | standards/components                                                  |
| Режимы, именование, палитра, генерация      | CLAUDE §2, §4–5, §14.2                               | standards/tokens                                                      |
| Источник, fallback, размеры иконок          | CLAUDE §6.4, §0.2.4                                  | standards/icons                                                       |
| Адаптивность, focus, ARIA, keyboard         | CLAUDE §8–9, §14.4                                   | standards/accessibility                                               |
| Stories, ThemeCheck, описания               | CLAUDE §10, §14.3, §14.7                             | standards/documentation                                               |
| Figma parity и Code Connect                 | CLAUDE §0.2.3–0.2.4, §11                             | standards/figma                                                       |
| Проверки и завершение                       | CLAUDE §0.4, §14.1; quality-report/CI как реализация | standards/quality                                                     |
| SemVer, PR и публикации                     | CLAUDE §14.5–14.6, §18; PR template                  | standards/releases                                                    |
| Владение и настройки репозитория            | CLAUDE §15; CODEOWNERS; Cursor §2                    | standards/governance                                                  |
| Пошаговый процесс                           | CLAUDE §14; Cursor workflow                          | workflows/component с отсылками к стандартам                          |
| Примеры/история/старый бэклог               | CLAUDE §6.2, §10.2, §13, §16                         | references; действующие требования внутри истории выделяются отдельно |
| Подключение клиента и setup                 | Cursor; CLAUDE §1.1, §17                             | onboarding и адаптеры                                                 |

При переносе правила из §12 сохраняется ссылка на соответствующий стандарт; запрет не исчезает из-за того, что его подробности находятся в другом файле. Прикладные Component Specs остаются решениями конкретных компонентов. Workflows и скрипты инвентаризируются как механизмы исполнения, не как доказательство прохождения каждого требования.

## 6. Решения для рассмотрения

Рекомендации ниже ещё не изменяют действующие правила.

| ID  | Наблюдение                                                                                           | Предлагаемое решение                                                                                                             | Последствие                                                                                                      |
| --- | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| D1  | §0 требует полный протокол компонента; документы среды тоже нуждаются в отдельном маршруте           | Три масштаба: диагностика/docs; локальный ремонт по существующему Spec; новый/визуально изменённый компонент с полными матрицами | Изменение области gates требует принятия владельцем; обязательное качество сохраняется                           |

## 7. Перенос по проверяемым порциям

1. Рассмотреть структуру и D1–D10. Принятые ответы сохранить с датой и владельцем; несогласованные изменения смысла не переносить как утверждённые.
2. Подготовить нормативное ядро и стандарты по карте. Для каждой записи фиксировать фактическое место переноса, объединённые дубли и доказательство сохранения смысла. До переключения входа активен прежний контракт.
3. Переключить входные документы одной согласованной порцией. Старый текст сохранить в неактивном архиве; проверить отсутствие второго активного контракта и циклического чтения.
4. Подключить минимальные навыки и маршруты, затем task state и CLI. Права клиента остаются технической границей; текстовая роль «read-only» их не заменяет.
5. Испытать багфикс, компонент, docs, audit, возобновление сессии и отсутствие Figma. Новые навыки сравнивать с baseline на одинаковых задачах; включать отрицательные маршруты.
6. Подключать иконки/графики отдельными пилотами после выбора переносимых файлов, ревизий и лицензий. Общие Figma/токены/качество остаются применимыми к их поставке.

Существующие quality:report, CI и Foundations расширяются, когда потребуется реализация. Тексты правил проверяются review; доступные автоматические команды покрывают только свои заявленные области. Сборка Storybook не подтверждает визуальную паритетность, Code Connect parse — публикацию, наличие схемы — её исполнение.

## 8. Граница результата P0.2

Подготовлены проект структуры, маршруты, инвентаризация шести основных источников и решения для рассмотрения. Не выполнены перенос нормативных текстов, установка навыков, изменение Node/CI, интеграция ассетов и миграция компонентов. Следующий этап P0.3 начинается с принятых решений и проверки карты переноса, а не с автоматического сокращения CLAUDE.
