# Доступность и адаптация

Для затронутого поведения проверить реальные сценарии выбранного компонента и применимый паттерн, сохраняя согласованный визуальный контракт.

- Семантические HTML-элементы, labels и доступные имена. Button по умолчанию type=button, toggle — aria-pressed.
- Видимый focus-visible, корректный переход фокуса, без двойного outline/shadow.
- Loading отражается aria-busy и действительно блокирует мышь/клавиатуру; pointer-events недостаточно.
- aria-disabled с сохранением фокуса требует определённого сценария и управления взаимодействием.
- Ошибка поля связывается через aria-invalid и aria-describedby.
- Modal/Drawer: focus trap, Esc, aria-labelledby/описание. Tabs/Accordion: применимые стрелки/Home/End.
- Проверять контраст, клавиатуру, assistive technology и темы; автоматический axe/PASS не удостоверяет всю доступность.
- Мобильная область взаимодействия должна соответствовать принятому минимуму и контексту. Числовой минимум берётся из профиля и Spec выбранного проекта; не менять оптическую геометрию master без решения — при необходимости отдельно проектировать hit area.
- Проверять reflow, zoom, overflow, контейнеры и контент; адаптивность mobile-first, по применимости container queries.

Контрастные ориентиры текущего профиля: 4.5:1 обычный текст, 3:1 крупный текст и значимые интерактивные границы. Это инженерные критерии, не заявление о юридической сертификации.

Использовать реально существующие layout-примитивы системы. Экран — типизированная React-композиция; запланированный одноимённый layout не считается готовым UI-компонентом. Точные breakpoints, hit area и focus roles находятся в профиле и Spec выбранного проекта.
