# Документация и примеры

Один Component Spec владеет требованиями компонента; Storybook и пользовательские docs соответствуют реальному API и принятому контракту. Каталог строится по исходникам/exports/stories; ручные старые отметки не доказывают зрелость.

Stories нового/изменённого компонента имеют понятные props/описания, autodocs и первую интерактивную Default story. Controls и forced demo states не блокируют реальные hover/active/focus. Дальше показываются согласованные варианты и применимые состояния; универсальная AllVariants не обязательна.

Размеры/состояния соответствуют Spec. Не добавлять искусственные заголовки или числовые префиксы ради сортировки. ThemeCheck обновляется для новых/изменённых взаимодействий и тем. Конкретное оформление демонстраций находится в собственных docs выбранного проекта и не задаёт правила другой системе.

Foundations использует существующий генератор/каталог вместо второго ручного источника. Storybook build, interaction, visual и a11y — отдельные результаты. Установка более нового manifest/MCP/фреймворка не выполняется как скрытая часть документационной правки.

Исследования/решения/история остаются в системе; docs объясняют установку, использование, темы, развитие и ограничения. Ссылки передаваемой системы не требуют родительской среды. [Проверка](quality.md).

Директивы разработчика оформляются по [общему формату](../../templates/project-instructions.md#directive). Их действия/переходы не дублируются в справке: PROCESS задаёт общий маршрут, skills выбирают процедуру, standards задают требования, templates — формы.
