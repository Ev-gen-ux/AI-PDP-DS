# Проверки и доказательства

Выбирать методы по изменённому требованию и реальным потребителям. Пользоваться существующими scripts/config выбранной системы. Количество тестов и coverage сами по себе не являются критериями готовности.

## Масштаб

- Локальная правка: проверить описание/ссылку либо воспроизведение, причину и соседние ветки ремонта. Полные матрицы не пересоздаются.
- Компонент/новый контракт: все применимые разделы Spec, API/состояния/токены/stories/темы/a11y/mapping и совместимость.
- Выпуск: полный предусмотренный профиль выбранной поставки. Для кода — pipeline, пакет/consumer, changesets и необходимые ручные результаты; для Figma — целевая библиотека, привязки и визуальные критерии; для both — обе стороны и паритет. Это не автоматическая публикация.

Для токена учитывать примитив → семантика → потребители → примеры/темы. Для общего компонента — импорты/композицию. Динамический кандидат не равен точной ссылке; ограниченный каталог не доказывает полный граф влияния. При невозможности надёжно ограничить влияние расширить проверку и явно указать границы.

## Методы

- Документ: формат, локальные ссылки и соответствие текущему источнику.
- Логика: проектный typecheck, файловый lint, существующие релевантные unit/regression tests; новый тест только для нужного поведения.
- Визуальный контракт: реальный рендер выбранной поставки — browser/Storybook для кода, Figma для Figma; геометрия, состояния и темы. Для both проверяются обе стороны.
- Доступность: реальные клавиатура/фокус/семантика и настроенные автоматические методы.
- Генератор/упаковка: воспроизводимость, exports, ESM/CJS/types/CSS/SSR и реальный consumer.
- Среда: маршруты, ссылки/metadata, сохранность, негативные сценарии, concurrency и восстановление. Статическая структура не доказывает поведение агента в новом чате.

## Команды и область

Компонентный quality:report принимает --component и --change docs|logic|visual; --plan не пишет данные. Без аргументов сохраняется полный pipeline. Неизвестные/неполные аргументы не запускают всё автоматически. Новый канонический Spec ищется в component-specs/<id>/spec.md; старый docs/\*-component-spec.md — только переходный fallback.

В текущем профиле typecheck проектный. Logic выполняет выбранные unit-файлы, visual сохраняет требование ручного review. Отсутствие tests/Spec или ручного результата не превращается в полную готовность. Автоматический анализ diff/полного графа зависимостей не реализован.

Форматирование/lint применять к scope, без незапрошенного autofix. Перед commit выполнить предусмотренные format/check/typecheck/lint/test; commit/PR сами требуют полномочий. Команды tokens/build/quality могут менять generated output/coverage/reports: заранее сохранить существующие изменения. Не повторять успешно выполненный набор без новых изменений, ошибки или открытого риска.

## Evidence

Хранить метод, дату, ревизию/хеши значимых входов, результат, артефакты и ограничения в задаче/Verification. Pass, fail, not-run и not-applicable различаются. Исключение — явное решение владельца о конкретном критерии/версии; not-run остаётся not-run.

Сборка не доказывает взаимодействия/визуальный паритет; parse — публикацию; структура skills — их обнаружение клиентом. Chromatic onlyChanged/exitZeroOnChanges не означают принятие визуальных изменений; покрытие token/generated-only изменений требует отдельного подтверждения. Старые отчёты не подставляются вместо нового запуска.

Refresh не делает старое evidence актуальным. Приёмка владельца, технический результат и внешняя поставка — отдельные записи. Не выполнять пропущенные проверки по одному наличию поля accepted и не назначать owner acceptance самостоятельно.
