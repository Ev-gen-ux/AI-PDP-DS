# Требования к задачам

Обязательный стандарт. [Общий контракт](../../../AGENTS.md) задаёт полномочия; [решение 001](../decisions/001-environment-architecture.md) определяет согласованные изменения процесса.

## Масштаб и начало работы

Перед изменениями определить действие, объект, платформу, поставку, границы разрешённых правок, исходный источник/ревизию и критерий готовности. Изучить существующую реализацию и применимые стандарты; явно сообщить краткий kickoff. Не выдавать предположение за требование.

- **Диагностика, аудит, документация:** краткий scope и ожидаемый результат. Полные компонентные матрицы не нужны при отсутствии изменений компонента. Аудит выпускает findings и evidence, не исправляет код без поручения.
- **Локальный ремонт:** существующий API/Spec и минимальный diff; зафиксировать причину, затронутые состояния и релевантную регрессионную проверку. Обновить изменённые части Spec. Если Spec отсутствует, создать одну краткую запись источников API/тестов и границ ремонта, не выдумывая визуальную матрицу. Полный пересбор всех матриц не нужен для невизуальной правки, если принятые ограничения не меняются. Неизвестное в затронутой области выясняется до зависимой реализации.
- **Новый компонент или изменение визуального контракта:** Component Kickoff и полный Spec до кода. Нужны источник Figma либо явно принятый code-first источник, состояния, stories, a11y и done criteria. Пройти все применимые матрицы и проверки ниже.

Ясные рутинные действия в пределах поручения выполняются без повторного согласования каждого шага. Существенное новое визуальное решение, breaking API, конфликт источников и исключение из стандарта должны быть согласованы до зависимой реализации. Независимую авторизованную работу можно продолжать, фиксируя конкретный блокер.

## Единый Component Spec

Использовать [существующий шаблон](../../templates/component-spec.md); один канонический Spec на компонент. Task state ссылается на Spec и не повторяет матрицы.

1. Kickoff: компонент, источник, stories, a11y, done criteria.
2. Variant Matrix: appearance, size, state/status, selected, loading, icons и другие применимые оси.
3. Numeric Map и Figma → Token Map: padding T/R/B/L, gap, radius, font-size, line-height; точное значение источника → семантический токен → resolved value.
4. State Token Matrix: все применимые сочетания appearance/state/selected/loading с background, border, label, icon, padding, height и radius.
5. Hard Constraints: неизменяемые размеры, заливки, padding, radius и другие ограничения.
6. Verification: fidelity, engineering, ThemeCheck, mapping, review и ограничения доказательств.

Матрица соответствует props, style maps и stories. Новая ось/значение сначала заносится в Spec, затем реализуется. Матрицы расширяются по задаче и не подменяются фиксированным универсальным набором.

Состояние длительной задачи хранит scope, ссылки на Spec/ревизии, принятые решения, неизвестные, проверки и следующий шаг. История и общие знания хранятся отдельно. Не сокращать и не перезаписывать существующие записи автоматически.

## Неизвестные и завершение

Сначала перечислить существенные неизвестные, задать необходимые вопросы и зафиксировать ответы. При конфликте источников или недоступном обязательном входе не угадывать зависимое решение. Не объявлять завершение по одному зелёному тесту: техническая проверка, ручной review и приёмка владельцем — разные результаты.
