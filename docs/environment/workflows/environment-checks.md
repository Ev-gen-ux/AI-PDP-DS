# Диагностика и маршруты среды

После [входа в задачу](task-start.md) определить, проверяется структура инструкций или конкретная локальная задача. Выполнить нужную команду из корня выбранной рабочей копии; из подпапки CLI находит Git root, явный `--root` позволяет проверить другую файловую копию без AI-клиента. Команды читают файлы, не исправляют их, не вызывают сеть и не исполняют method из evidence.

```sh
npm run --silent env:check
npm run --silent env:check -- --task environment-p11
npm run --silent env:route -- --action repair --object component
npm run --silent env:route -- --action audit --object component --mode parity
```

Вывод — JSON. env:check возвращает код 1 при нарушении, 0 при прохождении структурных проверок. env:route принимает только явно классифицированные action/object/mode; это таблица маршрутов, а не понимание свободного текста. Неизвестные параметры и несовместимые режимы завершаются ошибкой. Для icons/chart/environment пока нет специализированного default implementation-навыка: запрос корректен, но ответ содержит `supported: false`, причину и предметные стандарты. Это не подтверждение реализации.

## Что проверяется

- [Registry](../registry.json): единственный машинный реестр путей, предметных требований и совместимости маршрутов. Порядок действий хранится в workflows, нормативный текст — в standards. При добавлении/переносе инструкции обновлять реестр и навигационные ссылки в одной задаче.
- Присутствие общих и предметных ссылок в AGENTS/адаптерах, индексах и навыках; соответствие инвентарей каталогов реестру. Маршрут audit не может указывать на навык с несовместимым action/object. Общие tasks/quality добавляются независимо от навыка.
- Канонические имена/описания навыков, их уникальность и дубли имён в проектных .claude/.cursor/.codex skills. В текущем контракте метаданных поддержаны однострочные name/description (plain, JSON double-quoted либо YAML single-quoted); многострочные и другие поля требуют расширения валидатора. Это ограниченный проектный формат, не полный YAML parser. agents/openai.yaml и клиентские policy этим валидатором не сертифицируются.
- Относительные файловые Markdown-ссылки, reference definitions и CLAUDE @ imports. Примеры в fenced/inline code не считаются активными ссылками. Поддержана используемая в среде форма Markdown; anchors, внешние URLs и полноценный Markdown AST не проверяются. Выход за рабочую копию и symlink в сканируемых инвентарях отвергаются. Архивные страницы не сканируются как действующие инструкции.
- Неизменность замороженной исходной карты, покрытие всех её ID реестром миграции, существование целей/ADR и разделение active/archive. Четыре точных исходных текста проверяются через legacy-sources.json и SHA-256; Markdown-представления имеют отдельные контрольные хеши, поскольку содержат заголовок неактивного архива и историческое форматирование. Семантическая эквивалентность переноса остаётся предметом review.
- Схема задачи соответствует загруженной runtime-схеме. Только явный `--task` дополнительно вызывает существующий валидатор состояния: stale inputs/evidence, статус, Spec и приёмка. По умолчанию приватные .local/tasks не читаются и не публикуются. Вывод диагностики не содержит тела выбранной задачи.

`--mode intake|research|parity` добавляет нужный подготовительный маршрут; audit сохраняет аудит. Work — основной режим по умолчанию. Разрешение на внешнюю запись не вычисляется CLI: `externalAuthorization: not-evaluated` требует учитывать фактическое поручение и права клиента.

## CI и интерпретация

Существующий quality:report запускает env:check и test:tooling. Структурный JSON находится в .local/quality/environment.json, лог — рядом; существующий GitHub Quality workflow загружает их в общем артефакте. Обычный CI также запускает env:check и tooling-тесты; format:check явно включает скрытый каталог навыков.

Для дефекта сначала изучить finding и соответствующий diff. Править только в рамках поручения; аудит сам не разрешает изменение инструкции. Пройти [проверку и передачу](verify-deliver.md). PASS относится к структуре на текущих файлах: он не означает завершение задачи, owner acceptance, визуальный паритет или успешную публикацию. Тесты поведения агента, автоматическое обнаружение и клиентские hooks проверяются отдельно в P1.2.
