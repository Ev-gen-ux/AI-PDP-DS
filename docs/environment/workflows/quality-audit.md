# Аудит и разбор качества

После [входа](task-start.md) открыть [индекс quality](../domains/quality.md) и стандарты проверяемого объекта. Зафиксировать исходную ревизию и существующие изменения, критерии и доступные источники. Порученный аудит не превращать в реализацию рекомендаций.

Начать с чтения кода/Spec, существующих логов и CI-артефактов. Привязать результат к точному headSha/входам: старый зелёный run не подтверждает текущий код. Если нужна новая команда, сначала проверить её побочные эффекты. `quality:report` регенерирует файлы и сборки; для строгого чтения использовать имеющиеся evidence либо отдельную временную копию, когда такой запуск допустим. Не запускать format --write, autofix, sync/publish или обновление source files в аудитируемой папке.

Для дефекта отделить симптом от проверяемой причины. Для каждого finding указать:

- приоритет и конкретное последствие для пользователя/сопровождения;
- файл/строку или внешний источник и ревизию;
- воспроизведение/наблюдение, ожидаемое и фактическое;
- факт либо гипотезу, рекомендацию и ограничения проверки.

Не выдавать непокрытый сценарий за доказанный дефект. Результаты группировать по влиянию; отсутствие найденных проблем описать вместе с проверенным scope. В конце сверить рабочее дерево с началом, отдельно сохранить только заказанный отчёт/состояние. Пройти [передачу](verify-deliver.md), не исправляя исходники и не выставляя owner acceptance.
