# Работа с компонентом

После [входа в задачу](task-start.md) прочитать [индекс компонентов](../domains/components.md) и его применимые стандарты. Выбрать одну из веток по фактическому изменению; при переходе между ветками сохранить один Spec и состояние задачи.

## Новый компонент или новый вариант

Прочитать существующие компоненты, токены, stories и экспорты: сначала проверить возможность расширения принятого решения. Из master/согласованного code-first источника и Spec установить API, варианты, состояния, числовые карты и критерии приёмки. Неизвестный существенный контракт передать в уточнение/проектирование до зависимого кода.

До реализации нового варианта обновить Spec. Затем создать реализацию, типы, стили, stories и mapping в соответствии со стандартом components; подключить экспорты и применимые примеры/ThemeCheck. Для нового компонента без источника не копировать произвольные значения соседа как утверждённый дизайн.

## Ремонт или доработка существующего

Воспроизвести симптом на текущих входах, сопоставить ожидаемое поведение со Spec/API и выделить причину. Если дефект не подтверждён, отделить гипотезу от факта и проверить её до правки. Прочитать затронутую логику и соседние состояния; сохранить принятые API и поведение вне scope.

Невизуальный ремонт требует релевантной записи источников и проверки поведения. Если изменяется визуальный контракт/API или добавляется вариант, применить требования соответствующей новой/визуальной ветки, обновить затронутый Spec и согласовать ещё не определённое решение. Не проводить полный новый бриф для уже принятого локального ремонта.

Внести минимальное достаточное изменение. Регрессионная проверка должна воспроизводить прежний симптом и проверять исправленное поведение; масштаб автоматических и ручных проверок выбрать по реальному риску. Обновить затронутые stories, mapping, ThemeCheck и документацию по стандартам, когда изменилось их поведение или описание.

## Проверка и результат

Проверить type safety до следующей зависимой работы. Для затронутого визуального контракта сверить реальные состояния/темы с принятым источником; для mapping разделить локальный parse и разрешённую публикацию. Выполнить [проверку и передачу](verify-deliver.md).

Выход: компонент/правка, единый актуальный Spec, применимые примеры/экспорты/mapping, причина ремонта и evidence с ограничениями. Аудит заканчивается findings и не запускает реализацию автоматически.
