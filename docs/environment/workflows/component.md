# Работа с компонентом

Процедура дополняет обязательные стандарты из [индекса компонентов](../domains/components.md) и [tasks](../standards/tasks.md).

1. Определить масштаб: локальный ремонт по существующему Spec либо новый/визуально изменённый контракт.
2. Прочитать код, токены, stories и существующий Spec. Источник Figma обязателен для затронутого визуального контракта и соответствующей Figma-поставки; невизуальный ремонт опирается на принятые требования и проверки поведения. Использовать доступные инструменты текущего клиента, а не устаревшие имена из примера.
3. Сформировать kickoff и критерии завершения. Заполнить/обновить один Spec и необходимые матрицы до зависимой реализации. Существенные неизвестные уточнить, решения зафиксировать.
4. Работать в отдельной ветке на актуальной принятой базе. Реализовать только порученный scope; проверить type safety перед следующими зависимыми действиями.
5. Обновить stories, применимый mapping, публичные экспорты и ThemeCheck. Проверить затронутые интерактивные состояния и темы; визуальное соответствие источнику проверяется при затронутом визуальном контракте.
6. Выполнить релевантные команды качества; записать ревизии и ограничения. Применимые ручные и публикационные проверки не заменять локальным parse/build.
7. Оценить версию, changeset и миграцию. Открыть PR с evidence, дождаться предусмотренных проверок и review. Публикацию выполнять в рамках разрешённой поставки.
8. Обновить Spec и документацию по фактическому результату; незавершённые зависимости отметить явно.

Обычный багфикс не требует повторного большого брифа, если требования и полномочия уже известны. Новый вариант сначала меняет Spec. Аудит заканчивается findings и не запускает эту процедуру реализации автоматически.
