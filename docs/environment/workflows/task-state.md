# Состояние задачи и возобновление

CLI запускается из рабочей копии проекта: `npm run env:task -- <command>`. Для чистого JSON без npm-заголовков использовать `npm run --silent env:task -- <command>` либо прямой запуск Node. Из подпапки можно вызвать скрипт по его пути: корень определяется через Git; `--root` явно выбирает корень другой рабочей копии. Нужны установленный Node и Git, сетевые сервисы не используются.

## Создание

```bash
npm run env:task -- init repair-example
npm run env:task -- resume repair-example
```

Создаётся `.local/tasks/repair-example/state.json` с версией схемы, ID, revision, Git HEAD и временем. Неизвестные title, route, scope, Spec и следующий шаг остаются `null`. Повторный init отказывает даже для уже существующей пустой папки; флага перезаписи нет. Данные задачи и журналы остаются в игнорируемом `.local/`.

Для известных вводных сохранить, например, `.local/task-seed.json` и выполнить `init repair-example --seed .local/task-seed.json`:

```json
{
  "title": "Исправить локальное поведение компонента",
  "route": {
    "action": "repair",
    "object": "component",
    "platform": "web-react",
    "delivery": ["code"]
  },
  "scope": {
    "summary": "Исправить согласованный дефект",
    "preserve": ["Публичный API"]
  },
  "spec": "docs/counter-component-spec.md",
  "inputs": ["src/components/counter/Counter.tsx"],
  "nextStep": "Подтвердить причину регрессионным сценарием"
}
```

Пути примера заменяются фактическими путями задачи. Spec хранится один раз: ссылка и SHA-256, без копирования матриц. `inputs` содержит другие объявленные входы. Для Spec и inputs в seed/patch разрешены строки путей: CLI сам получает хеши. В сохранённом state это объекты `{path, sha256}`. Дубли Spec/inputs, в том числе через символическую ссылку на один файл, отвергаются.

## Чтение и проверка

`resume` возвращает state, `token` (SHA-256 текущего JSON-файла), `fingerprint` объявленных входов, `stale`, `problems` и `validForCompletion`. Чтение не пишет файлы и не сокращает историю. Неизвестная версия схемы, неправильная структура и незнакомые поля вызывают ошибку без удаления данных.

`check` дополнительно требует соблюдения смысловых инвариантов и актуальности ссылок; ошибка даёт ненулевой exit code. PASS состояния discovery означает корректное незавершённое состояние, а не готовую задачу.

Fingerprint включает title, route, scope, sourceCommit, Spec, inputs, решения и вопросы. Изменения статуса, номера записи и следующего шага сами по себе не переатрибутируют результаты. Git HEAD и хеши файлов проверяются при чтении. Речь об **объявленных входах**: незаписанные зависимости и незакоммиченные файлы вне inputs инструмент не определяет автоматически.

## Обновление

Получить token через resume, записать patch в отдельный JSON и передать этот token:

```bash
npm run env:task -- update repair-example --expect TOKEN_FROM_RESUME --patch .local/task-patch.json
```

Patch заменяет только указанные верхние поля. Вложенные route/scope передаются полностью. Например, `{"status":"ready"}` меняет только статус. id, schemaVersion, revision, updatedAt и sourceCommit управляются инструментом и не принимаются в patch. Решения и вопросы сохраняются в соответствующих массивах; если решение уже канонически записано в Spec/ADR, хранить краткую ссылку, не вторую полную версию.

Все записи используют `write.lock`, повторную сверку token, сохранение точного прежнего JSON в history/ и атомарную замену state.json. Несовпадающий token означает конфликт: перечитать состояние и сопоставить изменения. CLI не объединяет их вслепую. История не очищается автоматически.

Lock координирует экземпляры CLI. Он не является транзакционной гарантией для произвольных внешних редакторов; инструмент проверяет ручные изменения повторно перед записью. После аварийного завершения lock может остаться: сначала проверить процесс по записанным PID/времени и сохранить состояние; автоматического снятия чужой блокировки нет.

## Статусы и доказательства

- discovery → ready → implementation → review → accepted.
- На готовность нужны известные title, route, scope, следующий шаг и решённые вопросы. Компонент/график требует канонический Spec, кроме чистого аудита.
- blocked требует конкретный blockedReason. Выход из блокировки требует его явного обнуления.
- Из review разрешён возврат в implementation. Из accepted — возврат в review; нельзя пропустить review при обычном продвижении.
- accepted требует явную запись `acceptance` с by, note и текущим fingerprint; нужны актуальные evidence с результатом pass. Отсутствие комментария не создаёт approval.

Evidence содержит kind (`automated`, `manual`, `publication`), method, result (`pass`, `fail`, `not-run`), fingerprint и artifacts. Артефакты — существующие файлы с хешами. Получить готовую ссылку:

```bash
npm run env:task -- ref .local/quality/report.json
```

Инструмент **не выполняет** строку method, не проверяет личность автора acceptance и не доказывает, что перечислены все обязательные проверки предметного стандарта. `validForCompletion` означает техническую согласованность записанного accepted с объявленными входами и доказательствами на момент чтения, а не независимую сертификацию результата.

## Изменились исходники

После review различий можно обновить снимок входов:

```bash
npm run env:task -- refresh repair-example --expect TOKEN_FROM_RESUME
```

refresh получает текущий HEAD и хеши Spec/inputs. Он не меняет fingerprints старых evidence и не обновляет хеши их артефактов. Если accepted устарел, состояние возвращается в review, а acceptance снимается; прежняя запись остаётся в history/. Дальше нужны актуальные проверки и отдельная запись приёмки. Отсутствующий Spec или артефакт не создаётся автоматически.

Схема: [task-state.schema.json](../schemas/task-state.schema.json). Runtime исполняет ограниченный набор ключевых слов именно этой схемы, без внешних зависимостей: типы, enum/const, обязательные/неизвестные поля, границы/паттерны строк, минимум чисел, items/minItems/uniqueItems и локальные ссылки $defs. Неподдержанный ключ останавливает загрузку. Это не универсальный JSON Schema validator; формат дат, пути, статусы, ревизии и актуальность дополнительно проверяются предметной логикой.

Тесты входят в существующий `npm run test:tooling` и, следовательно, в `quality:report`. Регистрация агентских навыков и автоматическое возобновление через hooks остаются последующими этапами.
