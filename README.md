# AI-PDP-DS

**Дизайн-система, которая объединяет Figma, дизайн-токены, React-компоненты и правила разработки с AI.**

AI-PDP-DS — открытый проект библиотеки интерфейсных компонентов. Его задача — сделать путь от макета до реализации понятным и проверяемым: одинаково описывать варианты и состояния, использовать общие токены, документировать поведение и проверять изменения до публикации.

[Посмотреть Storybook](https://main--69f08a5c57bcf2747e61c70d.chromatic.com/) · [Макеты в Figma](https://www.figma.com/design/i7T3ru2M0SyXgJeTda8f43/AI-PDP-DS) · [Сообщить об ошибке](https://github.com/Ev-gen-ux/AI-PDP-DS/issues)

## Текущий этап

Проект находится в активной разработке. Компоненты доступны в публичном Storybook, исходный код можно запустить и развивать в собственном форке.

Проверена поставка библиотеки: тема и CSS со шрифтами включены в архив, проверены ESM/CJS, серверный рендер и подключение в отдельном приложении Vite. Полный прогон на Node 20 включает 175 тестов компонентов, 17 тестов инструментов и автоматический отчёт качества.

**Пакет для установки — `@evgeni_design_84/ai-pdp-ds`.** Его можно подключить через npm или собрать архив из исходников командой `npm pack`. Button успешно опубликован в Code Connect для React через CLI. Для Variables REST API отдельно нужны Enterprise и scopes чтения/записи, которых нет у текущего токена. Это не мешает запуску библиотеки и Storybook.

Подробности поставки и настройки интеграций: [library-setup.md](docs/library-setup.md). В [аудите готовности](docs/readiness-audit.md) сохранены исходные проблемы и результаты исправлений.

## Какую проблему решает проект

Между макетом и готовым интерфейсом легко появляются расхождения: одинаковые элементы получают разные отступы, состояния существуют только в Figma, а изменения приходится переносить вручную. Когда в работе участвует AI, добавляется ещё один риск: агент может правдоподобно воспроизвести внешний вид, но придумать размеры, свойства или поведение, которых нет в исходном компоненте.

AI-PDP-DS выстраивает общий процесс для дизайна и реализации. Варианты компонента описываются до кода, числовые значения связываются с токенами, состояния показываются в Storybook, а проверки дают обратную связь перед слиянием изменений. Цель — сокращать число неявных решений и делать результат воспроизводимым.

Проект служит и библиотекой компонентов, и примером организации работы над дизайн-системой. Наличие процесса не означает, что каждый исторический компонент уже прошёл все описанные в нём проверки: такие пробелы фиксируются отдельно.

## Что входит в систему

- **Основные элементы:** Button, ButtonIcon, ButtonLink, Icon, Avatar, Label и Divider.
- **Ввод и выбор:** InputText, InputSearch, InputEmail, InputTel, InputDate, DatePicker, Checkbox, Radio, Toggle, Select, Multiselect и SelectButton.
- **Файлы:** FileUpload и InputFile.
- **Навигация и раскрытие контента:** Breadcrumbs, Sidebar, SidebarNavigationItem, TabGroup, TabItem, Accordion, Pagination, Stepper и StepperGroup.
- **Обратная связь:** InlineMessage, NotificationSnackbar, StatusLabel, StatusMark, Counter, Spinner и ProgressBar.
- **Составные элементы:** Modal, ModalDialog, BenefitCard, SplitButton, ToggleButton и Chips.
- **Табличные примитивы:** TableRow, TableColumn и варианты TableCell, включая текст, выбор, статус, редактирование и слоты.
- **Компоновка:** Stack, Cluster и Grid.

Конкретные свойства и доступные состояния следует смотреть в stories и типах выбранного компонента. Перечень не означает одинаковую полноту проверки каждого компонента и не обещает наличие всех элементов, упомянутых в дорожной карте.

## Методология и источники истины

Система строится вокруг трёх связанных уровней:

1. **Дизайн:** мастер-компоненты Figma задают визуальные варианты, значения и ограничения.
2. **Токены:** сохранённые в репозитории JSON-файлы позволяют воспроизвести тему без обращения к Figma при каждой сборке.
3. **Реализация:** React-код задаёт публичный API и поведение; Storybook показывает примеры его использования.

При разработке нового компонента визуальные значения сверяются с конкретным мастер-узлом Figma. Уже существующий компонент служит примером структуры кода, но не заменяет проверку размеров и токенов. Если источники противоречат друг другу, контракт требует уточнить расхождение до реализации.

Изменение в Figma не обновляет библиотеку автоматически само по себе. Его нужно получить через предусмотренную интеграцию или согласованный перенос, проверить diff токенов, собрать тему и проверить компоненты. Аналогично наличие mapping-файла ещё не подтверждает опубликованную связь Code Connect.

## Как устроены токены и темы

В `tokens/primitives/` хранятся исходные значения палитры, размеров и базовой типографики. В `tokens/semantic/` — значения с назначением: например, фон кнопки определённого вида и состояния, отступы или радиус компонента.

Команда `npm run tokens:build` запускает Style Dictionary и создаёт:

- `src/theme/tokens.ts` — объект `theme` и его TypeScript-тип;
- `src/theme/variables.light.css` — базовые значения и светлую тему;
- `src/theme/variables.dark.css` — цветовые переопределения тёмной темы;
- `dist/figma.tokens.json` — JSON-артефакт токенов, который сам по себе ещё не является готовым запросом к Figma Variables API.

Компоненты получают объект через `ThemeProvider` из styled-components. Значения объекта ссылаются на CSS-переменные. Поэтому подключения одного `ThemeProvider` недостаточно: CSS темы должен быть загружен в приложение.

В текущем Storybook светлая и тёмная темы переключаются атрибутом `data-theme`; объект `theme` остаётся общим. Типографика предусматривает режимы XL, MD и XS с переопределениями на ширинах 1280 и 768 пикселей. Корректность всех адаптивных значений в обеих темах требует отдельной визуальной проверки: зелёная сборка её не заменяет.

Сгенерированные файлы не редактируются вручную. Изменения вносятся в исходные токены, после чего тема пересобирается.

## Контракт и работа с AI

[CLAUDE.md](CLAUDE.md) — основной контракт проекта. Название файла историческое: документ описывает правила работы с библиотекой, применимые к AI-агентам и разработчикам, а не отдельную реализацию компонента. Перед задачей его нужно прочитать и явно определить применимые требования.

Контракт задаёт:

- порядок уточнения требований и подготовки спецификации;
- приоритет мастер-компонента Figma при выборе визуальных значений;
- использование семантических токенов и строгих типов;
- правила интерактивных состояний, фокуса и доступности;
- структуру stories и проверку светлой и тёмной тем;
- проверки перед коммитом, Pull Request и выпуском версии.

[cursor_instruction.md](cursor_instruction.md) дополняет контракт онбордингом и дорожной картой. Он не заменяет основной документ. Внешние сервисы и MCP могут давать агенту контекст макета, но не отменяют проверку результата человеком.

Контракт — инструкция для участников процесса. TypeScript, ESLint, тесты и CI автоматически проверяют только часть его требований. Полнота соответствия Figma, корректность выбранного токена и качество всех состояний требуют отдельного просмотра. Нельзя считать чтение контракта технической гарантией соблюдения каждого правила.

## Как создаётся компонент

1. **Kickoff.** Определяются компонент, источник в Figma, состояния, stories, проверки доступности и критерии готовности.
2. **Спецификация.** По [единому шаблону](docs/templates/component-spec.md) фиксируются Variant Matrix, Numeric Map, State Token Matrix и Hard Constraints: оси вариантов, точные значения, выбранные токены и ограничения мастер-компонента.
3. **Реализация.** Пишутся типизированные свойства и стили на токенах. Служебные стилевые свойства используют префикс `$`, чтобы не попадать в DOM.
4. **Документация поведения.** Default позволяет исследовать компонент через Controls; демонстрационные stories показывают варианты и состояния.
5. **Проверка.** Выполняются автоматические команды и сверка с Figma. Для новых компонентов и изменений интерактивного поведения обновляется Foundation/ThemeCheck.
6. **Изменение через PR.** Код проходит review и CI. При изменении публичного API добавляется Changeset с объяснением изменения и типом версии.
7. **Публикация.** После слияния в `main` GitHub Actions публикует Storybook в Chromatic при корректно настроенном проекте и секрете.

Для документации и инфраструктурных задач применяется соответствующая часть процесса. Матрицы визуальных состояний нужны при работе над компонентами; их не следует формально создавать для каждого изменения текста.

## Поиск ошибок и аналитика качества

Диагностика состоит из нескольких уровней. Каждый отвечает на свой вопрос:

| Уровень                | Инструмент                                           | Что проверяет                                                          |
| ---------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------- |
| Исходные данные        | Diff токенов и спецификация                          | Что изменилось и соответствует ли изменение задаче                     |
| Типы                   | TypeScript                                           | Согласованность типов и публичных интерфейсов                          |
| Статический анализ     | ESLint, Prettier                                     | Правила кода и единое форматирование                                   |
| Поведение              | Vitest, Testing Library                              | Сценарии, описанные в тестах компонентов                               |
| Интерактивная проверка | Storybook, addon-a11y                                | Поведение, варианты и обнаруживаемые инструментом проблемы доступности |
| Темы                   | Foundation/ThemeCheck                                | Совместный просмотр компонентов в светлой и тёмной темах               |
| Визуальные изменения   | Chromatic                                            | Отличия снимков опубликованных stories от базовой версии               |
| Поставка               | Сборка, проверка состава пакета, пробное подключение | Доступность кода, стилей и типов для потребителя                       |

В текущей конфигурации Chromatic визуальные отличия не блокируют CI: используется `exitZeroOnChanges`, а изменения в `main` автоматически принимаются как baseline. Поэтому успешный статус нельзя трактовать как подтверждение отсутствия визуальных дефектов.

### Как разбирается проблема

Для воспроизводимой ошибки нужно зафиксировать компонент, story, тему, ширину экрана, действия, ожидаемый и фактический результат. Затем определить слой причины: макет, токены, реализация, документация или упаковка. Исправление проверяется сначала целевым сценарием, затем необходимыми проверками проекта.

Наблюдения и исторические результаты проверок собраны в [docs/quality-metrics.md](docs/quality-metrics.md), вопросы связи с Figma — в [docs/figma-sync-audit.md](docs/figma-sync-audit.md). Даты этих записей относятся к конкретным проверкам; они не являются текущим статусом всей библиотеки.

**Аналитика качества представлена автоматическим отчётом GitHub Actions.** Команда `npm run quality:report` собирает результаты проверок, покрытие и журналы; Summary запуска и артефакт `quality-report` дают доступ к данным в GitHub. Отдельный аналитический кабинет и продуктовая телеметрия не входят в текущий сценарий. Отчёт не заменяет проверку пользовательских сценариев и ручной аудит доступности.

## Как изучать Storybook

Публичный Storybook можно открыть без установки проекта. Его назначение — дать работающий пример компонента и объяснить доступные свойства.

1. Выберите компонент в **Components** и откройте **Default**, где он предусмотрен.
2. В **Controls** меняйте доступные свойства, затем проверьте реальные hover, focus и клики.
3. Посмотрите демонстрационные stories с вариантами и состояниями.
4. Переключите **Theme** в панели инструментов.
5. Откройте **Docs** для описания и таблицы свойств, а **Foundation/ThemeCheck** — для обзора тем.

Раздел **Layouts** содержит примитивы компоновки. Текущая вводная страница — **AI-PDP-DS / Introduction**. Storybook демонстрирует опубликованный код, поэтому локальные изменения становятся видны на публичной ссылке только после публикации.

## Локальный запуск и свой форк

### Запуск исходного проекта

Целевая версия Node.js указана в `.nvmrc` — Node 20; в `package.json` заявлены Node.js от 20 и npm от 10. При настройке собственной среды следует согласовать версию Node с зависимостями и использовать lockfile.

```bash
git clone https://github.com/Ev-gen-ux/AI-PDP-DS.git
cd AI-PDP-DS
nvm use
npm ci
npm run tokens:build
npm run storybook
```

Storybook запускается на **http://localhost:6006**. Для этих шагов токены Figma и Chromatic не нужны: исходные JSON уже находятся в репозитории. Сначала собирается тема, поскольку её сгенерированные файлы не хранятся в Git.

### Работа в своём форке

Создайте fork в GitHub и клонируйте его адрес вместо исходного репозитория. После локального запуска создайте отдельную ветку для изменений. Для публикации и синхронизации потребуются ваши проекты, доступы и секреты: настройки и секреты автора не переносятся в fork автоматически.

До включения внешних интеграций проверьте `figma.config.json`, ссылки в `*.figma.ts` и исторических `*.figma.tsx`, метаданные `package.json`, `.github/CODEOWNERS` и workflow. Если используете собственную Figma-библиотеку, нужно сопоставить её структуру и идентификаторы с исходным кодом. Простая замена `FIGMA_FILE_KEY` не меняет связи компонентов.

## Подключение к приложению

Установите библиотеку и peer-зависимости:

```bash
npm install @evgeni_design_84/ai-pdp-ds react react-dom styled-components
```

Альтернативный способ — собрать архив из исходников:

```bash
npm pack
```

В приложении-потребителе установите полученный `.tgz` и peer-зависимости React, React DOM и styled-components:

```bash
npm install /путь/к/evgeni_design_84-ai-pdp-ds-1.0.0.tgz react react-dom styled-components
```

Имя архива зависит от текущей версии `package.json`.

```tsx
import { ThemeProvider } from 'styled-components';
import { Button } from '@evgeni_design_84/ai-pdp-ds';
import { theme } from '@evgeni_design_84/ai-pdp-ds/theme';
import '@evgeni_design_84/ai-pdp-ds/theme/variables.css';

export function App() {
  return (
    <ThemeProvider theme={theme}>
      <div data-theme="light">
        <Button text="Продолжить" />
      </div>
    </ThemeProvider>
  );
}
```

CSS включает обе темы, адаптивную типографику и шрифты. Для тёмной темы используется `data-theme="dark"`. Проверка `npm run package:check` устанавливает архив в отдельный проект и проверяет типы, импорты, SSR и сборку Vite. Проверяется установленный набор peer-зависимостей; полная матрица версий React требует отдельных прогонов.

## Интеграции и публикация

| Интеграция   | Состояние и настройка                                                                                                                                                                     |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Figma → JSON | `npm run tokens:pull`; нужны токен, file key, подходящий план и scope `file_variables:read`. Читаются `.env.local`, затем `.env`                                                          |
| JSON → тема  | `npm run tokens:build`; работает локально без внешних секретов                                                                                                                            |
| JSON → Figma | `tokens:push` создаёт план; `tokens:push:apply` применяет его без удалений. Нужны доступ к Variables API и read/write scopes. Shadow — effect styles, поэтому исключены с предупреждением |
| Code Connect | Шаблон Button проверен и опубликован через CLI. Code Connect поддерживает Professional с ограничениями, а также Organization/Enterprise; остальные mapping-файлы остаются заготовками     |
| Chromatic    | В исходном проекте публикация работает. В fork нужен собственный проект и `CHROMATIC_PROJECT_TOKEN`                                                                                       |
| Версии и npm | Changesets формирует изменения версий; отдельный ручной workflow проверяет и при явном выборе публикует пакет. Аутентификацию npm настраивает владелец                                    |
| Качество     | `quality:report` и GitHub Actions публикуют Summary, JSON, журналы и coverage-артефакты                                                                                                   |

Секреты не следует добавлять в код или публичные файлы. Для локального Figma pull передайте их через переменные окружения или игнорируемый Git файл `.env.local`. Для GitHub Actions настройте соответствующие repository secrets. Просмотр Storybook и обычная локальная сборка от них не зависят.

Постоянная ссылка Storybook указывает на последнюю успешно опубликованную сборку ветки `main`. Для фиксации конкретного состояния проекта можно использовать ссылку на отдельную сборку из Chromatic.

## Структура и команды

```text
tokens/          — исходные токены: primitives и semantic
src/theme/       — генерация темы, CSS-переменные, подключение шрифтов
src/components/  — компоненты, типы, stories, тесты и mapping-файлы Figma
src/layouts/     — Stack, Cluster и Grid
docs/            — Introduction, спецификации, метрики и аудиты
scripts/         — генерация токенов и инструменты интеграции с Figma
.storybook/      — настройки Storybook, тем и документации
.github/         — CI, публикации и правила review
CLAUDE.md        — основной контракт
cursor_instruction.md — онбординг и дорожная карта
```

| Команда                           | Назначение                                  |
| --------------------------------- | ------------------------------------------- |
| `npm ci`                          | Установка зависимостей из lockfile          |
| `npm run tokens:build`            | Генерация темы и CSS                        |
| `npm run storybook`               | Локальная интерактивная документация        |
| `npm run storybook:build`         | Статический Storybook в `storybook-static/` |
| `npm run typecheck`               | TypeScript                                  |
| `npm run lint`                    | ESLint без допустимых warnings              |
| `npm run test`                    | Vitest                                      |
| `npm run test:coverage`           | Тесты с отчётом покрытия                    |
| `npm run format` / `format:check` | Форматирование и его проверка               |
| `npm run build`                   | Токены, типы и сборка библиотеки в `dist/`  |
| `npm run changeset`               | Описание изменения для версии библиотеки    |

`npm run dev` запускает Vite, но проект не содержит готового приложения-песочницы с `index.html`. Основная точка входа для просмотра компонентов — Storybook.

## Ограничения и следующие шаги

Поставка архивом и проверки внешнего приложения подготовлены. Для полного внешнего выпуска остаётся:

1. Поддерживать проверку устанавливаемого пакета при последующих выпусках.
2. Решить, нужны ли платные интеграции Code Connect и Variables API; при использовании настроить план, scopes и проекты Figma.
3. По одному сопоставить остальные компоненты с опубликованными мастер-узлами Figma.
4. Расширить проверку совместимости React и провести визуальную проверку состояний, тем и адаптивности.
5. Продолжать документировать сценарии внедрения и ограничения интеграций.

Предложения и воспроизводимые ошибки можно оформлять в Issues. Изменения проходят через отдельные ветки и Pull Requests; изменения публичного API описываются Changesets. Правки основного контракта согласуются отдельно.
