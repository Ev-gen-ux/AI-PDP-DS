# Design System Developer

**AI-среда для проектирования, разработки и сопровождения самостоятельных дизайн-систем — от первого запроса до проверенной библиотеки компонентов.**

Design System Developer объединяет работу дизайнера, инженера и архитектора: брифование, исследование, выбор фундамента, спецификации компонентов, примитивные и семантические токены, Figma, React, TypeScript, styled-components, Storybook и проверку поставки. Пользователь описывает результат обычными словами, а ведущий агент выбирает процедуру, уточняет существенные вопросы и выполняет согласованную работу.

Внутри уже находится **[AI-PDP-DS](projects/ai-pdp-ds/README.md)** — реализованная дизайн-система, разработанная и развиваемая с помощью этой среды. Она служит примером результата: имеет собственные исходники, токены, спецификации, документацию, Storybook, зависимости и инструменты. Проект можно изучать внутри разработчика или передать отдельно.

Репозиторий раньше назывался `AI-PDP-DS`. Теперь его название отражает весь инструмент — `design-system-developer`; имя примерной библиотеки и npm-пакета `@evgeni_design_84/ai-pdp-ds` сохраняется.

## Зачем нужна среда

Дизайн-система требует согласованных решений на нескольких уровнях: визуальные роли, значения токенов, композиция компонентов, публичный API, поведение, темы и документация. При изменении одного уровня важно понимать, что должно измениться на остальных.

Среда организует эту работу вокруг явных источников и результатов. Компонент получает спецификацию до реализации. Цвет или размер изменяется в источнике токенов, затем пересобираются производные данные. Проверки выбираются по характеру изменения, а решения и ограничения сохраняются внутри проекта.

Это позволяет продолжать задачу после перерыва, передавать систему другому разработчику и разрабатывать несколько независимых дизайн-систем в одной среде. У каждой системы собственные зависимости и продуктовая история; настройки одного заказчика не становятся обязательными для остальных.

## Быстрый запуск

### Требования

- Git для клонирования и управления версиями.
- **Node.js 22** для разработки; версия задана в `.nvmrc`.
- **npm 10.9 или новее** и использование поставляемых lockfile.
- AI-клиент с доступом к локальным файлам и терминалу для работы по процессу.
- Доступный Figma-инструмент только для задач, которым действительно нужна Figma.

Корень разработчика и каждая кодовая дизайн-система устанавливаются отдельно. Общего npm workspace нет.

### Установка разработчика

```sh
git clone https://github.com/Ev-gen-ux/design-system-developer.git
cd design-system-developer
# При установленном nvm:
nvm use
npm ci
npm run env:check
npm test
npm run lint
npm run format:check
```

Если nvm не используется, сначала выберите Node 22 доступным способом. Локальная папка `.local/toolchains/` на машине автора не включается в репозиторий и не требуется получателю.

`npm ci` устанавливает инструменты корня. При собственном Git устанавливаются локальные hooks; папка без собственного Git не перенастраивает родительский репозиторий.

### Запуск примера в Storybook

Из корня разработчика:

```sh
cd projects/ai-pdp-ds
npm ci
npm run tokens:build
npm run storybook
```

Откройте адрес из терминала, обычно `http://localhost:6006`. Сначала генерируются тема и CSS из сохранённых JSON-токенов. Для локальной работы не нужны токены Figma, Chromatic или npm-публикации.

```sh
# Из папки projects/ai-pdp-ds:
npm run build
npm run storybook:build
```

Библиотека собирается в `dist/`, статический каталог — в `storybook-static/`. Основная поверхность просмотра компонентов — Storybook; команда `dev` не означает наличие готового приложения-песочницы.

## Как работать с AI

Откройте папку разработчика в используемом AI-клиенте и укажите ему прочитать [AGENTS.md](AGENTS.md). Ведущий работает в профиле Principal Design Systems Engineer / Architect с компетенциями специалиста уровня 10+ лет: архитектура компонентов, токены, Figma, реализация, доступность, совместимость и передача.

В Work Environment модуль расположен на верхнем уровне рядом с другими специализированными средами. Явная команда «Запусти разработчик дизайн-систем» передаёт управление этому же локальному входу. Самостоятельному клону Work Environment не требуется.

Примеры запросов:

> Создай новую дизайн-систему для внутреннего кабинета. Нужен Storybook; значения цветов и шрифты я передам файлом.

> В AI-PDP-DS исправь потерю фокуса у InputPassword. Публичный API сохраняем.

> Для выбранного проекта подготовь план замены примитивных цветов. Пока ничего не применяй.

> Проверь соответствие компонента его Spec и Figma. Сначала только отчёт.

Агент извлекает известное из запроса и источников, задаёт вопросы небольшими раундами и уточняет противоречия. Пользователь принимает существенные продуктовые, API и визуальные решения. Уже согласованный технический шаг не требует нового разрешения. Неизвестный параметр остаётся вопросом или предметом исследования.

Названия скиллов и CLI знать необязательно. Команда `env:route --request` помогает подобрать маршрут по ключевым словам; окончательный выбор ведущий делает по контексту.

## Архитектура среды

```text
design-system-developer/
├── AGENTS.md                 # роль ведущего, вход и обязательные правила
├── README.md                 # публичное описание и запуск
├── ARCHITECTURE.md           # подробный реестр структуры и владения
├── PROCESS.md                # общий жизненный цикл и переходы
├── BACKLOG.md                # открытые улучшения разработчика
├── agents/                   # роли отдельных исполнителей
│   ├── ds-library-reader.toml
│   ├── ds-researcher.toml
│   └── ds-reviewer.toml
├── skills/                   # выбор процедуры по задаче
├── directives/               # предметные действия и переходы
│   └── .order                # порядок навигации по процессу
├── docs/
│   ├── environment-guide.md  # практическое руководство
│   ├── limitations.md        # фактические границы возможностей
│   └── standards/            # требования к качеству результата
├── config/
│   └── routes.json           # связи задач, скиллов, директив и ролей
├── templates/                # формы и переносимый проектный набор
│   ├── specifications.md     # брифы, Spec и матрица
│   ├── project-instructions.md # инструкции проекта и формат директив
│   └── project/
│       ├── tooling.json      # манифест установки
│       ├── primitive-request.json
│       └── scripts/
├── scripts/
│   ├── environment/          # проекты, журналы, примитивы и экспорт
│   └── tests/                # регрессии инструментов разработчика
├── .github/                  # CI, CODEOWNERS и форма PR
├── .husky/                   # локальные Git hooks
├── package.json              # private package инструментов
├── package-lock.json         # независимый lock разработчика
├── .nvmrc                    # Node 22
├── eslint.config.js          # lint инструментов
├── .prettierrc.json          # форматирование
├── .prettierignore           # границы форматирования
├── .gitignore                # исключения секретов и runtime
├── .order                    # порядок Explorer
├── LICENSE
└── projects/
    └── ai-pdp-ds/            # пример самостоятельной дизайн-системы
```

`agents/` содержит роли исполнителей, `skills/` — инструкции выбора процедур. Рабочий порядок находится в `directives/`, требования — в `docs/standards/`, формы документов — в двух общих документах `templates/`. Установщик извлекает нужный именованный раздел и создаёт отдельную форму/инструкцию внутри проекта; заполненные brief и Spec сохраняют собственные места. JSON и исполняемые скрипты находятся в `templates/project/`. У каждой директивы восемь разделов: назначение, входы, условия начала, этапы, решения владельца, результат, проверка и продолжение/возврат.

В корне private package только инструменты среды. Реальные библиотеки находятся в `projects/` со своими package/lock и исходниками. Инструменты процесса могут копироваться в библиотеку версионированным набором; система не импортирует файлы разработчика для своей сборки.

Восстановимые `node_modules/` и локальная `.local/` создаются на машине пользователя. `.local/` хранит используемый runtime и временное выполнение; завершённые задачи перестройки и постоянные копии проектов там не накапливаются. Порядок Explorer задаётся `.order` и установленным ExplorerSorter; на работоспособность CLI сортировка не влияет.

[Полный реестр папок и файлов](ARCHITECTURE.md) описывает конкретные скиллы, директивы, шаблоны, скрипты и проверки.

## Как связаны инструкции, скиллы и агенты

| Уровень            | Ответственность                                                        |
| ------------------ | ---------------------------------------------------------------------- |
| AGENTS             | Профиль ведущего, владение и полномочия                                |
| PROCESS            | Общий маршрут задачи и правила переходов                               |
| config/routes.json | Машинное соответствие объектов, действий, скиллов и процедур           |
| Skills             | Выбор предметной процедуры и нужных условных веток                     |
| Directives         | Действия, входы, результаты, проверки и возвраты                       |
| Standards          | Требования к компонентам, токенам, доступности, документации и выпуску |
| Templates          | Формы brief/Spec/матриц и состав копируемых инструментов               |
| Scripts            | Исполняемые локальные операции и диагностика                           |
| Agents             | Отдельные исполнители фокусных подзадач                                |

Доступны скиллы `ds-intake`, `ds-system`, `ds-component`, `ds-tokens-themes`, `ds-research-design`, `ds-figma-parity`, `ds-quality-audit`, `ds-documentation` и `ds-release`. Они читаются явно из локальных файлов по маршруту. Автоматическое обнаружение скиллов конкретным клиентом для процесса не требуется.

Отдельные роли подключаются при необходимости:

- **ds-library-reader** — фокусная инвентаризация API, вариантов, токенов и композиции выбранного проекта.
- **ds-researcher** — независимое изучение открытого вопроса по первичным источникам.
- **ds-reviewer** — ограниченная независимая проверка значимого изменения относительно контракта и доказательств.

Малую ясную правку ведущий выполняет сам. Наличие TOML не означает, что отдельный агент уже запущен. Ведущий читает роль, передаёт её инструкции доступному инструменту делегирования и проверяет результат. Если делегирование недоступно, работа и её ограничения описываются фактически.

## Путь новой дизайн-системы

1. **Вход.** Определить имя/ID, цель и минимальные границы результата.
2. **Контейнер проекта.** Создать `projects/<id>` и Discovery, чтобы материалы с начала работы принадлежали системе.
3. **Бриф.** Уточнить потребителей, платформу, поставку, темы, источники, ограничения и критерии. Подтверждённое, предположения и вопросы разделяются.
4. **Исследование по необходимости.** Изучить влияющий на решение вопрос и сохранить источники, сравнение и вывод.
5. **Выбор фундамента.** Зафиксировать источник/версию, семантику, режимы, aliases и необходимые изменения.
6. **Техническое развёртывание.** После достаточного согласованного брифа подготовить выбранный шаблон внутри проекта.
7. **Примитивы.** Получить значения заказчика, показать матрицу и связанные последствия, согласовать план и применить значения.
8. **Компоненты.** Для каждого нового/изменённого контракта подготовить единый Spec и согласовать его до реализации.
9. **Поставка.** Выполнить кодовую, Figma или обе ветки; при обеих — проверить паритет.
10. **Проверка и review.** Выполнить подходящие методы, предъявить результат и ограничения.
11. **Приёмка и передача.** Зафиксировать реальное решение владельца и передать согласованный результат.

Это маршрут с условиями, а не требование выполнять все пункты при каждом запросе. Порядок реализации определяют бриф, принятый Spec и текущий STATE.

```sh
# Из корня разработчика:
npm run env:project -- create bank-ds --name "Bank DS"
npm run env:task -- list --project bank-ds
npm run env:task -- resume create-system --project bank-ds
```

`create` создаёт только папку, system.json и черновой Discovery. Команда не выдаёт готовую React-библиотеку. `install-tooling` копирует journal/quality/doc-инструменты, а технический шаблон выбирает и разворачивает ведущий по [project-setup](directives/project-setup.md). Готового универсального каталога starter-шаблонов сейчас нет.

## Другие рабочие сценарии

### Новый компонент

```sh
npm run env:task -- init add-input --project bank-ds --component input
```

В `component-specs/input/spec.md` фиксируются назначение, props, варианты, состояния, числовая карта, токены, композиция, доступность и проверки. После реального согласования текущего Spec выполняется реализация в выбранных носителях. Изменение публичной оси или поведения сначала отражается в контракте.

### Ремонт принятого компонента

```sh
npm run env:task -- init repair-password --project ai-pdp-ds --component input-password --action repair
```

Агент воспроизводит симптом, устанавливает ожидаемое поведение по текущему контракту и вносит достаточную локальную правку. Полный новый системный бриф не требуется. Если исправление меняет принятый контракт, затронутое решение согласовывается до зависимой реализации.

### Исследование и аудит

Результат — записка или findings с вопросом, источником, воспроизведением, последствием и рекомендацией. Read-only аудит не меняет продукт автоматически. Поручение исправить найденное переводит работу в соответствующую предметную процедуру.

### Продолжение

```sh
npm run env:task -- list --project ai-pdp-ds
npm run env:task -- resume repair-password --project ai-pdp-ds
npm run env:task -- check repair-password --project ai-pdp-ds
```

Продолжение восстанавливает существующую задачу. Замечание уточняет её текущий scope; новый самостоятельный результат получает отдельную задачу. Слово «продолжай» само по себе не назначает приёмку результата.

## Примитивы, семантика и типографика

Фундамент разделяет конечные значения и их назначение. Например, примитив палитры содержит HEX, семантическая роль описывает цвет границы определённого компонента и состояния, а компонент использует эту роль через существующую привязку.

При настройке внешнего вида меняются согласованные конечные значения примитивов. Имена семантики, типы, режимы и alias-цепочки сохраняются. Alias внутри примитивного слоя также остаётся alias. Новая независимая роль, режим или структура — отдельная доработка фундамента.

Заказчик может передать значения текстом, файлом или ссылкой. Ведущий приводит их к точным ключам и машинному предложению, показывает текущие/предлагаемые значения, происхождение и влияние. Произвольный PDF или текст не разбирается универсальным автоматическим парсером. Неуказанные оттенки не выдумываются: сохранение базовых значений или новый подбор обозначаются явно.

```sh
npm run env:primitives -- matrix --project bank-ds
npm run env:primitives -- plan --project bank-ds --input product-discovery/primitive-request.json
# После реального согласования показанного плана:
npm run env:primitives -- apply --project bank-ds --input product-discovery/primitive-request.json --expect PLAN_FINGERPRINT --note "Owner approved the displayed plan"
```

Эти команды работают после появления выбранного JSON-фундамента в проекте. Matrix/plan ничего не записывают. Apply проверяет актуальность плана и допустимость значений; затем отдельно выполняются генерация и проверки выбранной поставки. Статический граф ссылок не заменяет анализ динамических потребителей.

Шрифты не закреплены за примером: заказчик может предоставить название, ссылку или файлы; Google Fonts используется по его указанию. Проверяются реальные начертания, веса, языки, загрузка и геометрия. Доступность семейства в Figma и подключение font assets в коде проверяются отдельно.

Вложенные Label, Inline Message и другие DS-компоненты сохраняют собственные props и семантику. Родитель владеет ролями своего тела и не переопределяет семантику вложенного компонента ради перекраски.

## Где хранятся результаты

```text
projects/<system-id>/
├── system.json
├── product-discovery/
│   ├── brief.md
│   ├── _process_log.md
│   ├── research/
│   ├── decisions/
│   └── tasks/<task-id>/       # последующие общесистемные задачи
├── component-specs/
│   └── <component-id>/
│       ├── spec.md           # единственный живой контракт
│       ├── brief.md
│       ├── _process_log.md
│       └── tasks/<task-id>/   # последующие задачи компонента
├── src/
│   ├── components/
│   ├── layouts/
│   └── theme/
├── tokens/
│   ├── primitives/
│   └── semantic/
├── .storybook/
├── docs/
├── scripts/
├── package.json
└── package-lock.json
```

Это пример кодовой системы; ненужные папки для Figma-only не создаются. В Product Discovery находятся общесистемные материалы, в Component Specs — контракты и задачи компонентов. Код, токены и пользовательская документация имеют собственные места. Все они передаются вместе с проектом.

Текущее состояние задачи хранится в блоке STATE её `_process_log.md`: scope, документы/хеши, решения, вопросы, evidence и следующий шаг. Отдельный state.json не создаётся. Исторические ревизии сохраняются; `refresh` обновляет снимки входов, не переисполняя проверки и не подтверждая изменённый Spec.

Основные состояния: `discovery → ready → implementation → review → accepted`. Пауза, блокировка и отмена различаются. `review` означает готовность к рассмотрению, `accepted` — фактическую приёмку владельцем текущего результата.

## AI-PDP-DS — пример результата

AI-PDP-DS показывает, какую самостоятельную библиотеку можно разрабатывать и сопровождать средствами Design System Developer. На этом проекте применялись и развивались компонентные спецификации, работа с токенами, композиция существующих DS-компонентов, ремонт поведения, Storybook и проверка передачи. Разные части библиотеки имеют свою историю и полноту проверки; наличие примера не означает, что каждый исторический компонент прошёл все современные этапы процесса.

| Часть             | Что находится в примере                                                                |
| ----------------- | -------------------------------------------------------------------------------------- |
| Реализация        | React/TypeScript-компоненты и styled-components                                        |
| Каталог           | Stories, документация, Controls, темы и foundations                                    |
| Фундамент         | Примитивы, компонентная семантика, генератор темы/CSS                                  |
| Контракты         | Принятые Spec и история компонентных задач                                             |
| Поставка          | Публичные exports, types, CSS/fonts и проверка consumer                                |
| Самостоятельность | Собственные package/lock, scripts, configs, docs и workflow для отдельного репозитория |

В библиотеке есть кнопки и ссылки, поля ввода, выбор, навигация, обратная связь, составные и табличные элементы, а также Stack, Cluster и Grid. Точный состав и поддерживаемые props определяются текущими exports, stories и типами.

В Storybook можно начать с Foundation/Overview, Components/Button/Default и Components/InputPassword/Default. Затем изучить варианты компонента, Controls, переключение темы, документацию и Foundation/ThemeCheck. Собранный каталог показывает текущий код; публичные ранее опубликованные previews не обновляются одним только локальным изменением.

```sh
# Команды из папки примера:
npm run env:check
npm run typecheck
npm run lint
npm run test:coverage
npm run test:tooling
npm run build
npm run package:check
npm run storybook:build
npm run figma:check
# Полный автоматический профиль:
npm run quality:report
```

Для приложения-потребителя нужен `ThemeProvider`, публичный объект темы и CSS. Установка опубликованного пакета зависит от доступной версии в реестре; исходники этого репозитория можно собрать в архив самостоятельно.

```tsx
import { ThemeProvider } from 'styled-components';
import { Button } from '@evgeni_design_84/ai-pdp-ds';
import { theme } from '@evgeni_design_84/ai-pdp-ds/theme';
import '@evgeni_design_84/ai-pdp-ds/theme/variables.css';

export function App() {
  return (
    <ThemeProvider theme={theme}>
      <div data-theme="light">
        <Button text="Продолжить" />
      </div>
    </ThemeProvider>
  );
}
```

CSS поставляет переменные, темы и шрифты. Один ThemeProvider без CSS недостаточен. Подробности: [подключение](projects/ai-pdp-ds/docs/library-setup.md), [конвенции](projects/ai-pdp-ds/docs/library-conventions.md), [развитие библиотеки](projects/ai-pdp-ds/docs/development.md) и [README примера](projects/ai-pdp-ds/README.md).

## Проверки и критерии готовности

Среда проверяет структуру реестра, ссылки, metadata скиллов, роли, маршруты, журналы, установку проектных инструментов и ограничения операций. Корневой CI отдельно проверяет разработчик и AI-PDP-DS; вложенные workflows GitHub автоматически из корня не запускает.

При подготовке исходного состояния на Node 22 прошли 64 теста инструментов разработчика, 181 тест компонентов примера и 28 его tooling tests. Чистая отдельная копия прошла установку, все 11 проверок quality-профиля, сборку пакета и Storybook. InputPassword был открыт и отрисован в локальном Chrome. Это результаты конкретного проверенного состояния, а не гарантия будущих изменений; актуальный статус находится в [GitHub Actions](https://github.com/Ev-gen-ux/design-system-developer/actions).

| Проверка               | Что подтверждает                                          |
| ---------------------- | --------------------------------------------------------- |
| env:check              | Структуру и ссылки в заявленном scope                     |
| TypeScript/lint/format | Соответствие настроенным статическим правилам             |
| Unit/regression tests  | Поведение покрытых сценариев                              |
| Tokens/build           | Генерацию и сборку текущих источников                     |
| Package check          | Архив, установку consumer, types, ESM/CJS, SSR и CSS/Vite |
| Storybook build        | Возможность собрать каталог                               |
| Browser review         | Наблюдаемый результат конкретных состояний                |
| Figma parity           | Сравнение реально выбранных источников и состояний        |

Сборка и Code Connect parse не подтверждают полный визуальный паритет, ручную доступность или публикацию. Evidence различает `pass`, `fail`, `not-run`, `not-applicable`. Принятое исключение не превращает невыполненную проверку в PASS.

GitHub CI не публикует npm-пакет или Figma-библиотеку. Внешние публикации выполняются только по отдельному соответствующему поручению.

## Передача готовой системы

Для кодового проекта:

```sh
npm run env:project -- export ai-pdp-ds --out /путь/к/новой-папке-вне-разработчика
```

Получатель забирает одну папку системы с исходниками, токенами, Storybook, документами, Spec и необходимой историей. Экспорт исключает Git, приватные env, зависимости и одноразовые/generated outputs и создаёт source manifest с хешами. Целевая папка должна быть новой. Export сам не устанавливает зависимости и не подтверждает сборку: получатель или ведущий проверяет отдельную копию.

Текущий CLI требует кодовый профиль с package/lock, src и Storybook. Для Figma-only передаются собственная библиотека и проектные материалы по [Figma-процедуре](directives/figma-delivery.md); запрошенный офлайн-файл требует реального доступного экспорта Figma.

Самостоятельную систему можно поместить в отдельный репозиторий. Remote, ветка, commit/push и публикация определяются явным поручением. Корень разработчика не становится зависимостью приложения-потребителя.

## Backlog и развитие

Канонический список будущих улучшений самой среды — [BACKLOG.md](BACKLOG.md). Задачи конкретной библиотеки или компонента находятся внутри соответствующего `projects/<id>`. Наблюдение в Backlog фиксирует потребность; оно не означает, что работа начата или срок обещан.

На момент этой редакции открыты:

| ID      | Направление                                      | Ожидаемый результат                                                                             | Статус           |
| ------- | ------------------------------------------------ | ----------------------------------------------------------------------------------------------- | ---------------- |
| DSD-001 | Проверка взаимодействия специализированных ролей | Ограниченные реальные запуски reader/researcher/reviewer и фиксация фактического взаимодействия | Требует проверки |
| DSD-002 | Порядок Explorer после npm ci                    | Устойчивое повторное применение сортировки без переименования папок                             | Наблюдение       |

При изменении состава Backlog эта краткая сводка обновляется вместе с ним. Новая запись содержит наблюдение, ожидаемый результат, приоритет и статус. Перед внедрением уточняются scope и критерии; после изменения выполняются подходящие проверки, запись закрывается или удаляется.

Подключение разработчиков иконок и графиков обсуждалось и отложено. Сейчас они остаются отдельными соседними средами Work Environment; их копий и автоматического запуска внутри этого разработчика нет. Возврат к этой интеграции требует нового поручения.

## Границы возможностей

- Рабочая кодовая платформа — React web. Другие платформы не обещаются как готовые адаптеры.
- Агент ведёт процесс через доступные инструменты. Чтение Markdown само по себе не разворачивает библиотеку и не запускает помощников.
- Полный React starter и Figma-only export не реализованы одной универсальной CLI-командой.
- Primitive CLI поддерживает текущий JSON $type/$value и разрешённые конечные значения. Составные типы и aliases доступны для просмотра; ресурсы шрифтов и Figma обрабатываются отдельными шагами.
- Статические ссылки токенов не составляют полного графа динамического влияния.
- Figma-инструменты, их права и обязательные plugin skills проверяются для конкретного действия. Доступ к библиотеке или шрифту не предполагается по одному наличию ссылки.
- Локальная сборка и CI не заменяют пользовательскую приёмку, полный визуальный аудит или подтверждение внешней публикации.

Актуальные подробности — [limitations](docs/limitations.md). Правила качества и критерии конкретной системы берутся из её собственных документов и принятого Spec.

## Работа с репозиторием

После переименования для существующего локального клона:

```sh
git remote set-url origin https://github.com/Ev-gen-ux/design-system-developer.git
git remote -v
```

Для изменения среды определите задачу и её границы, обновите канонический процесс/инструмент и вызывающие ссылки, выполните применимые проверки. Корневые инструкции находятся в AGENTS, архитектура — в ARCHITECTURE, общий маршрут — в PROCESS. Их назначение сохраняется при расширении README.

Изменения компонентов выполняются внутри соответствующей системы и её принятого контракта. Секреты передаются транзиентно или через исключённые env; они не включаются в исходники, документы и публичные отчёты. Существенные ограничения проверки описываются в результате изменения.

Идеи и воспроизводимые проблемы можно обсуждать в [Issues](https://github.com/Ev-gen-ux/design-system-developer/issues). Для вклада через PR используйте [шаблон](.github/pull_request_template.md) и применимые стандарты. Commit/push и публикации выполняются при соответствующих полномочиях.

Лицензия исходников — [MIT](LICENSE). Права и условия внешних зависимостей, шрифтов и подключаемых сервисов сохраняются отдельно.
