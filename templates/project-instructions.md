# Организация и сопровождение проектов

Канонические заготовки инструкций. [Манифест](project/tooling.json) выбирает именованный раздел и целевой путь; установщик извлекает его содержимое. Все проектные выходы самостоятельны, без импорта родительской среды. Версия и хеши установленного набора находятся в system.json.tooling.

| Раздел                                      | Назначение / выход                  | Зависимость                                                                      |
| ------------------------------------------- | ----------------------------------- | -------------------------------------------------------------------------------- |
| [project-agents](#project-agents)           | AGENTS.md выбранной системы         | Локальные Discovery/Spec, metadata и scripts                                     |
| [project-development](#project-development) | docs/development.md                 | Установленный journal/quality/primitive набор, собственные package/config        |
| [directive](#directive)                     | Формат новой директивы разработчика | [Стандарт документации](../docs/standards/documentation.md) и актуальный процесс |

Постановка и контракт берутся из [specifications.md](specifications.md). Установка по [project-setup](../directives/project-setup.md) не создаёт React-библиотеку и не устанавливает её зависимости. Существующие файлы изменяются только при совпадении управляемого хеша; локальные конфликты не перезаписываются. Формат директивы предназначен для автора процедур и не копируется в каждый проект автоматически.

Внутри ограждений ссылки рассчитаны на готовый выходной путь. Markdown-ссылки агента из project-agents работают из корня системы, из project-development — из её docs/. При установке формы brief/Spec/матрицы извлекаются в локальные templates, чтобы автономные задачи не зависели от разработчика. Старые установленные системы не обновляются автоматически.

## project-AGENTS

<!-- TEMPLATE:project-agents:START -->

```markdown
# Работа с этой дизайн-системой

Папка самостоятельна: используй только её package/config/scripts, Discovery, Spec и исходники. Проект и имя пакета определяются system.json и package.json; родительская среда не требуется.

Начинай с product-discovery/brief.md и актуального STATE журнала задачи. Один живой spec.md компонента находится в component-specs/<id>, реализация — в src/components/<id>. Последующие задачи компонента имеют собственные brief/журнал в tasks/<id>. Отдельный state.json не создаётся.

Новый/изменённый компонентный контракт согласовывается до кода; ясный ремонт сохраняет принятый API. Вложенные DS-компоненты сохраняют свои props и семантику. Правь исходники токенов, не generated output.

Команды журналов: env:task list/resume/check/update/refresh/approve-spec. Сначала проверяй --help и package scripts. Refresh не превращает старые результаты в PASS. Приёмка требует реального решения владельца о текущей версии.

Проверки выбираются по diff и Spec; pass/fail/not-run/not-applicable фиксируются отдельно. Не выдавай сборку за визуальную/ручную проверку. Не публикуй и не выполняй Git-записи без явного поручения. Секреты не сохраняй.

[Развитие проекта](docs/development.md). Общие инструменты скопированы сюда версионированным набором; их обновление не должно затирать локальные изменения.
```

## project-development

<!-- TEMPLATE:project-development:START -->

````markdown
# Развитие дизайн-системы

[AGENTS](../AGENTS.md) задаёт локальный вход. Общий бриф, исследования и решения находятся в product-discovery. Контракт компонента — component-specs/<id>/spec.md; код — src/components/<id>. Документы/история передаются вместе с этой папкой.

## Задача

```sh
npm run env:task -- init repair-button --component button --action repair
npm run env:task -- list
npm run env:task -- resume repair-button
npm run env:check
```

Остальные опции — env:task --help. STATE журнала является единственным текущим состоянием. Для update нужен --expect TOKEN последнего чтения; patch передаётся файлом либо --patch - через stdin. История сохраняет прежние Markdown-ревизии.

Заполните brief, согласуйте новый/изменённый Spec, затем переходите discovery → ready → implementation → review. Только фактическая приёмка владельца разрешает accepted текущего результата. Изменения входов требуют refresh, анализа diff и новых затронутых проверок; предыдущие receipts остаются историей.

## Настройка примитивов

Значения проекта находятся в tokens/primitives; семантические ключи, типы, режимы и aliases сохраняются. После выбора версии фундамента используйте `npm run env:primitives -- matrix`, затем `plan --input product-discovery/primitive-request.json`. Формат предложения — templates/primitive-request.json, форма согласования — templates/primitive-matrix.md.

В предложении values сопоставляет точные ключи конечным значениям, sources — ключи их происхождению, fonts — список {family, source, reference?}; source равен client, google-fonts или existing. Неуказанные значения сохраняются, aliases доступны только для чтения. Apply требует --input, --expect fingerprint показанного плана и --note реального согласования. Устаревший план не применяется. Генерация, подключение произвольных шрифтов, проверка метрик и выбранная поставка storybook/figma/both выполняются отдельно; команда не подтверждает их готовность.

## Набор инструментов

Версия и хеши установленных файлов находятся в system.json.tooling. Файлы копируются, не импортируются из родителя. Получатель может пользоваться ими независимо; обновление набора выполняется отдельно и отказывает при конфликте с локальной правкой.

Набор предоставляет журналы, диагностику документов и компонентный запуск quality:report. Он не поставляет готовую React-библиотеку или зависимости. Для реального проекта нужны собственные package-lock, конфигурации, исходники, темы, Storybook, тесты и CI. Поддержанные команды сверяйте с package.json.

Реальная передача проверяет одну изолированную копию: npm ci, сборку, проверки, пакет и Storybook по контракту проекта. Наличие этого документа/набора не означает, что передача выполнена.
````

## directive

<!-- TEMPLATE:directive:START -->

```markdown
# Формат рабочей директивы

Использовать при создании и изменении процедур разработчика. Подставить предметное название и содержательные правила; не оставлять пустые заголовки. Достаточность процедуры определяется решениями и результатом, а не её длиной. Общие требования связывать ссылками с docs/standards, формы — с templates; профиль ведущего остаётся в AGENTS.md.

## Назначение и запуск

Какую задачу решает процедура, откуда вызывается, какие режимы применимы. Указать границы анализа/реализации и выбор поставки, если они влияют на действия.

## Входы

Необходимые источники и канонические документы. Дать относительные ссылки на реально используемые процедуры/стандарты/формы. Значения конкретного проекта в глобальную директиву не включать.

## Условия начала

Что должно быть известно, доступно и согласовано до зависимых действий. Разделить минимальный вход и требования к более поздней реализации; не блокировать независимую разрешённую часть.

## Этапы

Действия в нужной последовательности, условия выбора ветки и точки перехода к другим директивам. Дублирующий процесс в docs/skills не создавать; привести нужные команды или сослаться на поддерживаемый инструмент. Возможности инструментов описывать фактически.

## Решения владельца

Какие существенные решения принадлежат владельцу и когда они нужны. Учитывать уже данные полномочия; рутинные шаги не превращать в новые согласования. Не выводить разрешение на внешнюю запись/публикацию из названия процедуры.

## Результат

Конкретные артефакты, их владелец/место и следующий содержательный результат. Сохранять проектные brief/Spec/STATE внутри проекта, без дублирующего хранилища.

## Проверка

Наблюдаемые критерии, применимые методы и ограничения доказательств. Различать pass/fail/not-run/not-applicable, реализацию, внешнюю запись и приёмку. Автоматизация проверяет только заявленную область.

## Продолжение и возврат

Повторный запуск, актуальные источники/ручные изменения, возврат после замечания или ошибки, условия остановки зависимой части. Называть следующий маршрут; сохранять историю проекта и не переиспользовать устаревший evidence.
```
